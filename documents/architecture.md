## Модульный монолит

Приложение — **один процесс** (`app/`, бинарник `nexus`), но код разделён на **модули** по
бизнес-задачам. Каждый модуль — отдельный crate в Cargo workspace.

| Модуль | Отвечает за | URL |
|---|---|---|
| [`auth`](modules/auth.md) | регистрацию, вход (пароль, письмо, OAuth), токены, роли | `/api/v1/auth` |
| [`catalog`](modules/catalog.md) | контент (фильмы, книги, ...), людей, теги, поиск | `/api/v1/catalog` |
| [`social`](modules/social.md) | форумы, рецензии, оценки, коллекции, подписки | `/api/v1/social` |
| [`realtime`](modules/realtime.md) | WebSocket: уведомления, чаты | `/ws` |

```
app/ (nexus)  ──собирает──►  modules/auth, catalog, social, realtime
                                     │
                                     ▼
                              libs/shared  (конфиг, БД, AppState, ошибки, логи, проверка JWT и ролей)
```

### Правила границ

1. **Модули не зависят друг от друга**, только от `libs/shared`. Это проверяет CI
   (`scripts/check-module-boundaries.sh`): зависимость одного модуля от другого валит сборку.
2. **Каждый модуль работает только со своими таблицами.** Чьи таблицы чьи — в документах модулей.
3. Проверка доступа (`AuthUser`, `AdminUser`, `Role`) лежит в `shared`, а не в модуле `auth`:
   права проверяют все модули, а зависеть от `auth` им нельзя. Модуль `auth` только выдаёт токены.
4. Если модулю нужны данные другого (например, `social` проверяет, что сущность существует), то это
   делается через явный публичный интерфейс (трейт в `shared`), а не через SQL в чужие таблицы.
   Сделано так: `shared::directory` (`EntityDirectory` реализует catalog, `UserDirectory` — auth),
   реализации лежат в `AppState`, см. [social.md](modules/social.md#чужие-данные-справочники).
5. Если модулю нужно сообщить другим о том, что произошло (новое сообщение в теме), он публикует
   событие в `shared::events::EventBus` (`state.events`), а не вызывает другой модуль: так `social`
   сообщает `realtime`, см. [realtime.md](modules/realtime.md).

### Почему монолит, а не микросервисы

Сначала проект был задуман как четыре микросервиса. Мы перешли на модульный монолит, потому что
на текущей стадии микросервисы дают в основном издержки:

- **Одна транзакция вместо распределённой.** «Создать тему и прикрепить к ней фильм и книгу» —
  это одна транзакция в одной БД. В микросервисах это пришлось бы согласовывать между сервисами.
- **Проще разработка.** Одна сборка, один контейнер, один деплой, отладка в одном процессе.
  Собрать четыре сервиса через `cargo watch` — это четыре компиляции и много памяти.
- **Масштабирование остаётся.** Нагрузку (например, от форума) держим, запуская несколько копий
  всего приложения за балансировщиком: приложение не хранит состояние в памяти между запросами.
- **Путь к микросервисам открыт.** Благодаря строгим границам модуль можно вынести в отдельный
  сервис, когда для этого появится реальная причина (отдельная команда, особая нагрузка).

Цена: ошибка, которая роняет процесс, роняет всё приложение. Защищаемся тестами и CI, а
паники в обработчиках запросов axum не роняют сервер.

## Абстрактная сущность

Всё содержимое каталога — фильмы, сериалы, книги, игры — лежит в **одной таблице `entities`**.
Тип хранится в поле `kind`. Все социальные функции ссылаются на `entities.id` и не знают,
фильм это или книга.

```
                    ┌──────────── entities ─────────────┐
                    │ id, kind, slug, title,            │
                    │ description, release_date,        │
                    │ cover_url, metadata (jsonb)       │
                    └─────────────────▲─────────────────┘
          ┌──────────────┬────────────┼────────────┬──────────────────┐
     entity_tags   entity_credits  reviews   collection_items   forum_thread_entities
                                                                 user_interests
```

**Как устроено:**
- Общие поля (название, описание, дата выхода, обложка) — обычные колонки. Списки, сортировка и
  поиск по всем типам работают без JOIN.
- Поля, специфичные для типа (длительность фильма, ISBN книги, платформы игры), лежат в
  `metadata jsonb` с GIN-индексом, так что по ним тоже можно фильтровать.
- Структуру `metadata` для каждого типа описывает и проверяет код модуля `catalog`. Сама БД её не
  проверяет: это плата за гибкость.

**Как добавить новый тип контента (например, комиксы):**
1. Миграция: `ALTER TYPE entity_kind ADD VALUE 'comic';`
2. В `catalog`: описать структуру `metadata` для комикса и её валидацию.

Форумы, рецензии, коллекции и интересы заработают сразу: они ссылаются на `entity_id`.

**Почему одна таблица с `jsonb`, а не базовая `entities` + отдельные `films`, `books`:**
отдельные таблицы дают строгие типы в БД, но каждый новый тип — это новая таблица, новые
JOIN'ы и правки во всех запросах «по всем типам» (поиск, ленты, коллекции). Мы выбрали скорость
добавления типов. Если у какого-то типа появятся сложные данные со своими связями (например, сезоны
и эпизоды сериала), для них заводится отдельная таблица со ссылкой на `entity_id`. Абстрактная
сущность при этом остаётся центром.

## База данных: общие соглашения

- Первичные ключи — `uuid` v7 (`DEFAULT uuidv7()`, встроена с PostgreSQL 18): не раскрывают число
  записей и генерируются где угодно, а первые 48 бит — время в миллисекундах. Поэтому новые строки
  ложатся в конец индекса первичного ключа, а не в случайную страницу, как у v4 (`gen_random_uuid()`):
  индекс не разбухает и вставки на больших таблицах (форум, рецензии, лента) не замедляются; `id`
  сортируются по времени создания. Цена — по id видно время создания, у нас оно и так публично
  (`created_at`). Строки, созданные до миграции `uuid_v7`, остались с v4 — тип тот же, всё совместимо.
  Тест `uuid_keys_default_to_v7` не даст завести таблицу с v4.
- `created_at` / `updated_at` — `timestamptz`. `updated_at` обновляет триггер `set_updated_at()`.
- Публичные идентификаторы в URL — `slug` (`/catalog/dune-2021`), а не id.
- Удаление родителя каскадно удаляет зависимые записи (`ON DELETE CASCADE`).
- Расширения: `pgcrypto` (раньше — `gen_random_uuid()`), `citext` (email и username без учёта регистра), `pg_trgm` (поиск
  по подстроке).
- Миграции — `migrations/*.sql`, применяются при старте приложения. Применённые файлы не редактируем.

## Инфраструктура

```
браузер / фронтенд
        │  http://localhost  (порт 80)
        ▼
     nginx  ──────►  app (nexus :8080)  ──►  PostgreSQL :5432
                                         ──►  Mailpit :1025 (SMTP, dev)
                                         ──►  Redis :6379
                                         ──►  Meilisearch :7700
```

- **Монорепозиторий.** Весь код — в одном Cargo workspace: `app/`, `modules/*`, `libs/*`.
- **nginx — единая точка входа.** Фронтенд ходит на один адрес (`http://localhost/api/v1/...`).
  Адрес приложения nginx переспрашивает у DNS Docker, поэтому пересоздание контейнера `app` его не ломает.
  Маршрутизацию по модулям делает само приложение, а nginx проксирует запросы и включает
  апгрейд соединения для WebSocket. Позже на нём же можно делать TLS и раздачу статики.
- **Hot-reload в Docker.** Исходники монтируются в контейнер, `cargo watch` пересобирает и
  перезапускает приложение при сохранении. Кэш крейтов и сборка (`/target`, вне папки проекта)
  вынесены в Docker volumes, поэтому пересобирается только изменённый код. Обычно это секунды, а не
  минуты, как при первой сборке.
- **Инструменты в Docker.** Сервис `tools` с тем же тулчейном: `make ci-docker`, `make test-docker`,
  `make shell` — Rust на машине не обязателен.
- **Production-образ** (`infra/Dockerfile`): сборка в образе с Rust, запуск в `debian-slim`
  без компилятора. Размер около 90 МБ. CI публикует его в GHCR с тегом sha коммита.
- **Staging и прод** — `infra/docker-compose.prod.yml`: тот же образ, разные `infra/.env.prod`.
  Подробно, включая чек-лист подключения сервера, — [deploy.md](deploy.md).

## Кэш чтения ✅

Карточки сущностей и людей (`GET /catalog/entities/{slug}`, `GET /catalog/people/{slug}`) читаются по
цепочке из трёх уровней. В PostgreSQL этот запрос не ходит. Детали, таблица записи и тесты —
[catalog.md](modules/catalog.md#кэш-карточек-).

```
L1 moka (память процесса, 30 с) ─промах─► L2 Redis (JSON, 24 ч) ─промах─► L3 Meilisearch (поле card)
   ▲ попадание в L2 → записать в L1          ▲ попадание в L3 → записать в L1 и L2
```

- **Строго три уровня.** Карточки нет в Meilisearch → `404`. Meilisearch недоступен → `503`, но то,
  что уже лежит в L1 и L2, отдаётся. Это осознанный выбор: читающая нагрузка не идёт в БД. Цена —
  при падении Meilisearch карточки, которых нет в кэше, недоступны.
- **Meilisearch хранит карточку целиком.** В документах индексов `entities` и `people` есть поле
  `card` — тот же JSON, что API отдавал из БД. Поле не участвует в поиске, и `GET /search` его не отдаёт.
- **Источник правды — PostgreSQL.** Админка пишет в БД. Затем `search::sync` обновляет документы в
  Meilisearch и **дожидается применения**, и только после этого сбрасываются L1 и L2. Если сбросить
  кэш раньше, промах успеет снова заполнить Redis старой карточкой из Meilisearch.
- **Перестройка по расписанию** (по умолчанию раз в сутки, `SEARCH_REINDEX_INTERVAL_SECS`) — страховка
  от расхождений, если `sync` не прошёл. После подмены индексов карточки в Redis сбрасываются. При
  нескольких инстансах перестраивает один — блокировка в Redis.
- **Другие инстансы** видят старую карточку в своём L1 не дольше 30 с. Это принимаем; позже —
  рассылка инвалидации через Redis pub/sub.
- **Redis не ломает ответы.** Ошибка, таймаут (100 мс) или битый JSON — warning в лог и переход к L3.
- **Общий код** — `shared::cache` (L1, L2, правила); что и откуда грузить при промахе, решает модуль.
  Списки, теги и справочники для `social` (`EntityDirectory`) по-прежнему читают из БД.

## Качество

- **Тесты:** unit-тесты рядом с кодом; тесты с БД через `#[sqlx::test]` (каждый тест получает чистую
  базу); HTTP-тесты без сети через `nexus::build_app`.
- **HTTP-проверки:** `http/*.http` для HTTP Client в JetBrains, `make http`.
- **CI** на каждый PR: форматирование, clippy, границы модулей, тесты, `cargo deny` (уязвимости и
  лицензии), сборка образа; в `main` — публикация образа.

## Открытые вопросы

- Отдельные Postgres-схемы для модулей (`auth.users`, `catalog.entities`, ...): граница модулей
  будет видна и на уровне БД. Решить до появления реальных данных.
- Фронтенд: React или Flutter.
- Где деплоить: на старте — VPS с `docker-compose.prod.yml` ([deploy.md](deploy.md)); Kubernetes —
  когда одной машины станет мало. Сервера пока нет.
