# Модуль `catalog`

**Отвечает за:** контентное ядро — сущности (фильмы, сериалы, книги, игры), людей и их роли,
теги, поиск через Meilisearch.
**URL:** `/api/v1/catalog` · **Код:** `modules/catalog/`

**Статус:** ✅ чтение (список с сортировками, карточки из PostgreSQL со связанными произведениями,
похожие, люди, теги и жанры), поиск через Meilisearch, админка с публикацией правок (поиск, ISR
фронтенда) и потоком шагов (SSE), перестройка поиска без простоя с версиями индексов, проверкой
размера и потоком прогресса, мини-дамп, каталог фильмов из TMDB + Wikidata со слиянием источников (`scripts/catalog-import`).
🕓 фильтры по полям `metadata`, поиск людей в Meilisearch.

Почему всё лежит в одной таблице `entities` — в [architecture.md](../architecture.md#абстрактная-сущность).

## Таблицы

### `entities` ✅ — сущности (абстрактная сущность)

Главная таблица проекта. Одна строка — одно произведение любого типа. Форумы, рецензии,

**Индексы:** по `kind`; по `release_date` (новинки сверху); частичный
`(release_date DESC NULLS LAST, title, id) WHERE active` — список по умолчанию; GIN по `metadata`
(фильтры по полям типа); триграммный GIN по `title` (поиск по подстроке, `ILIKE '%дюн%'`).

**Горячий слой и архив.** В `entities` — только горячий слой. С 2026-10-14 это **все** фильмы
TMDB с русским названием (121 371) и 500 самых популярных иностранных — 121 871 строка; сидов,
сериалов, книг, игр и фильмов без TMDB на dev больше нет (удалены 2026-10-14, `make seed` вернёт
сиды). Остальные ~1,07 млн фильмов — «скелетом» в холодном архиве (Tantivy,
[«Холодный архив»](#холодный-архив-)); полные данные TMDB по горячему слою —
[«Полные данные TMDB»](#полные-данные-tmdb-). Текст ниже про «~1,2 млн» описывает каталог до архива.

**Активные и скрытые.** Каталог из импорта TMDB + Wikidata — ~1,2 млн фильмов, на сайте —
отобранная часть (~80 тыс.: топ по баллу «Рекомендуемые» и «Скоро премьера», см. «Сортировка и
активные»; невышедшие фильмы из TMDB скрыты и без флага). Скрытая
(`active = false`) хранится в БД, но на сайте её нет нигде: ни в `/entities`, ни в поиске (не
индексируется), ни в похожих, связанных и фильмографиях, не считается в `entities_count` тегов;
карточка `/entities/{slug}` — 404 для всех, кроме админа (админу — и скрытые связанные). Справочник
для других модулей по slug её не находит — `social` отвечает 404 на рецензии, оценки, отметки,
коллекции и темы по такому slug; по id (уже сохранённое) — находит. Причины: «тонкие» страницы без
русского названия и описания вредят SEO всего сайта, а поиск и статика на миллион страниц — это
гигабайты. Включить — `PATCH /admin/entities/{id}` с `active: true` (публикация: поиск добавит
документ, фронтенд по ISR соберёт страницу) или скриптом импорта. Скрыть — `active: false`: поиск
удалит документ, ISR получит 404 и удалит статику.

**`metadata` по типам** проверяет код `catalog` (`modules/catalog/src/metadata.rs`). Все поля

пробелы, пустые строки и списки отбрасываются, дубли в списках убираются.

`awards` карточки берутся из таблиц `award_*` (см. ниже), а не отсюда.
Источник данных — `scripts/catalog-import/awards_wikidata.py` (Wikidata P166 и P1411, сопоставление
по id TMDB); у TMDB наград нет. Ручные записи редактора скрипт сохраняет.

Награды и номинации наполняет `scripts/catalog-import/awards_wikidata.py` (Wikidata P166 и P1411
через QLever, сопоставление по id TMDB; `requirements.txt` и venv — рядом со скриптом). Год —
квалификатор P585 утверждения, иначе дата церемонии (P805). Ручные записи редактора скрипт
сохраняет: их в Wikidata нет. Проверка на одном фильме — `--slug`, тогда запрос сужается до его
id TMDB. Когда QLever отвечает 502, для одного фильма годится `--endpoint
https://query.wikidata.org/sparql`; для всего каталога — нет, у WDQS таймаут 60 с.
Покрытие Wikidata неполное: у «Оппенгеймера» приходит 6 наград из семи «Оскаров».

**Новый тип** (комиксы, музыка): миграция `ALTER TYPE entity_kind ADD VALUE '...'`, вариант в
`EntityKind` (`models.rs`), структура и ветка `validate` в `metadata.rs`.

### Сезоны сериалов и серии ✅

Миграция `20261201100000_catalog_seasons.sql`.

Сезон — не вложенный объект сериала, а отдельная сущность: строка `entities` с `kind = 'season'`,
своим slug'ом (`arcane-season-2`, то есть `{slug сериала}-season-{номер}`) и сериалом в
`parent_id`. Slug генерится при создании и дальше живёт самостоятельно: переименование сериала
его не меняет.

Так сделано ради социального слоя. Оценка, рецензия, лайк, «буду смотреть», подборки,
комментарии и жалобы уже умеют работать с любым `{slug}` в `/api/v1/social/entities/{slug}/...`,
поэтому оценка сезона и рецензия на сезон появились без единой новой ручки. Был бы сезон
вложенным объектом — весь социальный слой пришлось бы писать второй раз, со своим хранением
голосов и своей модерацией. Оценка сериала целиком и оценки сезонов при этом не смешиваются: это
разные строки `entities`, у каждой своя сводка в `entity_ratings`, и на карточке сериала в
каталоге остаётся оценка сериала.

Сезоны не попадают в списки каталога и в поиск: в разделе «Сериалы» должен быть «Аркейн», а не
«Аркейн, сезон 1» и «Аркейн, сезон 2». В SQL за это отвечает условие `kind <> 'season'`
(константа `IN_CATALOG`) в публичном `GET /entities` и во всех запросах, наполняющих
Meilisearch. Админский список сезоны показывает — их надо находить и править. По прямому slug'у
сезон открывается и индексируется поисковыми системами: у него своя страница
`/series/arcane/season-2`, которая пересобирается вместе со страницей сериала (в её шапке
переключатель сезонов).

Поля сезона, кроме обычных полей сущности (`title`, `original_title`, `description`, `cover_url`,
`release_date` — это дата премьеры), лежат в `metadata`: `number` (номер, 0 — спецвыпуски,
единственное обязательное поле `metadata` во всём каталоге), `episode_count`, `status`
(`ongoing` / `ended` / `canceled`, как у сериала) и `finale_date` — дата выхода последней
вышедшей серии.

### `entity_fragments` ✅ — фрагменты полотна

Миграция `20261202100000_catalog_entity_fragments.sql`. Это лента «Интересные детали полотна» на
странице картины: карточка с крупным планом куска холста и подписью вроде «Скрытый автопортрет»
или «Аллегория гильдии».

Ключевое решение: фрагмент — прямоугольник на исходнике, а не отдельно залитый файл. С
координатами фронтенд из той же ленты перелетает зумом к этому месту на самом полотне: нажал
«Скрытый автопортрет» — картина увеличилась и показала лицо Рембрандта в толпе. В отдельных
JPEG это не сохранить, их можно только показать. Фрагмент при этом не сущность: ни оценок, ни
рецензий, ни своей страницы у «золотой девочки» нет и не будет — это часть картины, а не
произведение.

| Колонка | Тип | Ограничения | Описание |
|---|---|---|---|
| `id` | `uuid` | PK `uuidv7()` | |
| `entity_id` | `uuid` | NOT NULL → `entities(id)` CASCADE | Картина; у других типов фрагментов не бывает, это проверяет код |
| `title` | `text` | NOT NULL, до 120 символов | Подпись детали |
| `description` | `text` | до 600 символов | |
| `crop_x`, `crop_y` | `float8` | NOT NULL, 0–1 | Левый верхний угол прямоугольника в долях ширины и высоты исходника, а не в пикселях: исходник могут перезалить в другом разрешении, и доли это переживут, а пиксели — нет |
| `crop_width`, `crop_height` | `float8` | NOT NULL, больше 0 и не больше 1 | Размеры прямоугольника в тех же долях |
| `position` | `int` | NOT NULL, по умолчанию 0 | Порядок рассказа, как `position` у титров: детали идут по смыслу, а не слева направо |
| `created_at`, `updated_at` | `timestamptz` | NOT NULL | `updated_at` — триггер |

Ограничение `entity_fragments_crop_inside` держит прямоугольник внутри полотна (`x + width` и
`y + height` не больше единицы): вылезший за край кроп сервер IIIF молча обрежет, и фронтенд
покажет не то место. Фрагментов до 20 на картину.

Фрагменты приходят прямо в карточке (`fragments` в ответе `GET /entities/{slug}`): их мало, и
нужны они сразу, так что второго запроса фронтенду делать не надо. Отдельная ручка осталась для
админки и ленивой подгрузки.

Наполнение выполняется скриптом `scripts/seed_painting_fragments.py`, который читает данные из `seeds/paintings/*.json` (по файлу на картину со slug в имени) и идемпотентно обновляет `entities.metadata` (`analysis`, `iiif_base`) и `entity_fragments`. Скрипт валидирует границы кропов (`0 <= x,y <= 1`, `x+width <= 1`, `y+height <= 1`, площадь ≥ 3% во избежание мыла), лимиты строк (заголовки до 120, описания до 600, разбор до 10 000 символов) и структуру списков (3–6 фрагментов, 2–4 абзаца и 2–4 тезиса в разборе).

### Серии сезона ✅ — внутри `metadata` сезона

Серия — не сущность: ни своего slug'а, ни рецензий, ни подборок у неё нет. Больше она и не
строка таблицы: серии лежат списком `episodes` в `metadata` своего сезона. Отдельная таблица
`episodes` была убрана, когда стало ясно, во что она обходится: на девять тысяч сериалов в ней
набралось 1,26 млн строк, а на полном каталоге TMDB (236 тысяч сериалов) вышло бы около 150 млн
строк — и всё это ради списка под карточкой сезона. Серии не ищут и не оценивают, оценка и
отзыв осмысленны на уровне сезона, так что отдельные строки им не нужны. Если когда-нибудь
понадобится обсуждение отдельных серий, серию поднимут до сущности тем же способом, что сезон.
Видео у нас нет и не будет, поэтому полей «просмотрено», прогресса просмотра и позиции в серии
здесь нет даже на будущее.

Список всегда отсортирован по номеру, пустые поля в нём не хранятся. У серии есть: `id`
(сохраняется при перезаписи — на нём держится кэш фронтенда), номер (0–10000, уникален внутри
сезона), название и оригинальное название (до 300 символов), описание (до 2000), дата выхода
(невышедшие серии отдаются тоже — карусель покажет их неактивными с датой), длительность в целых
минутах (1–10000), кадр из серии 16:9 с размерами (только парой и только вместе с самим кадром;
постер сезона сюда класть нельзя — пропорции 2:3 против 16:9 ломают карточку), а также даты
создания и изменения. Дата изменения меняется только у тех серий, у которых действительно
поменялись поля, иначе каждый прогон импорта заставлял бы фронтенд пересобирать всю карусель.

Чтобы серии не утяжеляли каталог, везде, где они не нужны — список сезонов сериала, карточка
сезона, выборка сущности по slug'у и по id — метаданные читаются без них. Индекс по метаданным
тоже построен по выражению без серий, и фильтр по студии обращается к тому же выражению, иначе
индекс перестал бы работать. Редактирование сезона через админку серии не теряет: если в
присланных метаданных списка серий нет, прежний переносится в новый объект.

Оценок у серий нет (они не сущности): оценка сезона важнее оценки серии.

### Сериалы ✅ — `scripts/catalog-import/series_tmdb.py`

Топ сериалов TMDB (`kind = series`). Отдельный маленький скрипт, а не ветка конвейера фильмов
(`fetch_tmdb.py` → `merge.py`): тот рассчитан на 1,2 млн строк с кэшем, дампом id и слиянием с
Wikidata, здесь — сотня-другая прямыми запросами.

- **Отбор** — `/discover/tv`: `--source rated` (по умолчанию) — по рейтингу среди сериалов с 500+
  голосами (`MIN_VOTES`), `voted` — по числу голосов, `popular` — по популярности, `all` —
  объединение всех категорий; `--limit` (100 по умолчанию, 0 — все), `--min-votes` (порог
  голосов). Готовый `/tv/top_rated` не годится: он поднимает наверх свежие премьеры с десятком
  оценок. Для всего каталога есть `--source export` — официальный ежедневный дамп TMDB со всеми
  сериалами (около 236 тысяч), он скачивается и кладётся в кэш, а `--min-popularity` отсекает
  совсем безвестные.
- **Долгий прогон и обрывы.** Запросы к TMDB у обоих импортёров сериалов идут через общий клиент
  (`tmdb_client.py`): общий на все потоки потолок запросов в секунду (`--rps`, по умолчанию 45
  при лимите TMDB около 50), повторы с нарастающей паузой, а на ответ «слишком много запросов»
  все потоки выжидают указанное время, после чего темп снижается и восстанавливается. Прогон
  переживает обрыв сети и перезапуск: уже записанные сериалы отсеиваются по базе, а просмотренные
  (в том числе отбракованные без постера) — по файлу `--checkpoint`, который дописывается по ходу
  работы. Ctrl+C дорабатывает очередь и выходит. Скорость — около 28 сериалов в секунду, то есть
  полный дамп проходится за пару часов.
- **Данные** — `GET /3/tv/{id}?language=ru-RU&append_to_response=credits,videos,images` на сериал.
- **Запись**: `title` (ru, иначе `original_name`), `original_title` (если отличается),
  `description` (`overview`), `release_date` (`first_air_date`), `cover_url` — постер
  `image.tmdb.org/t/p/w780` (как у фильмов), `cover_width`/`cover_height` — размеры этой копии
  (ширина 780, высота по пропорциям оригинала из `images`), `metadata` — `seasons`, `episodes`,
  `status` (`Returning Series`/`Ended`/`Canceled` → `ongoing`/`ended`/`canceled`, прочие — пусто),
  `countries` (`origin_country`), `studios` (`production_companies`), `trailers` (YouTube из
  `videos`, официальные первыми, до 5). Участники: `created_by` → роль `creator`, первые 15
  `credits.cast` → `actor` с именем персонажа. Жанры — `/genre/tv/list` (ru + en, slug как у
  фильмов, где id совпадают); нет тега — создаётся. В `entity_stats` пишутся `tmdb_popularity` и
  `tmdb_votes`.
- **`external_ids = {"tmdb_tv": id}`, а не `tmdb`** (индекс `entities_external_tmdb_tv_uq`,
  миграция `20261127100000_external_tmdb_tv.sql`). Две причины, обе ломающие: у TMDB независимые
  пространства id фильмов и сериалов (1399 — и фильм, и «Игра престолов»), общий
  `entities_external_tmdb_uq` отверг бы такой сериал как дубль; и условие `external_ids ? 'tmdb'`
  по всему каталогу значит «фильм из TMDB» — по нему считается `visible`, «Пересобрать активные»
  гасит всё, что не вошло в топ по баллу «Рекомендуемые», туда же смотрит перенос в холодный
  архив. Под ключом `tmdb` сериалы погасли бы при первом же пересчёте.
- Slug: транслит оригинального названия, затем русского (у японских и корейских оригиналов
  транслит пуст: «進撃の巨人» → `ataka-titanov`), в последнюю очередь `<base>-tv<id>`.
- Балл «Рекомендуемые» считается только по фильмам (`ranking.rs`), поэтому у сериалов
  `rank_score` пуст и в сортировке по умолчанию они идут последними; работают `rating`, `popular`,
  `trending`, `new`, `title`.
- Повторный прогон безопасен: записанные id пропускаются (и не запрашиваются у TMDB). После
  прогона — `scripts/index-entities.sh <slug'и>` (скрипт печатает готовую команду).

### Исходники картин и IIIF ✅ — тот же `paintings_wikidata.py`

Фрагменты без исходника высокого разрешения бессмысленны: кропнуть девять процентов полотна на
превью шириной 1000 px — это каша из пикселей. Поэтому импорт картин теперь пишет и исходник.

`image_url` — копия из Commons около 3000 px по ширине: берётся прямой адрес копии из
`imageinfo`, без лишнего редиректа и без служебных параметров. Тонкость: запрошенную ширину
MediaWiki округляет вверх до стандартной «корзины» — просишь 3000, получаешь файл шириной 3840,
а в ответе API ширина остаётся запрошенной. Поэтому ширину скрипт читает из самого адреса, а
высоту считает по пропорциям оригинала: в базе должны лежать размеры того файла, который
скачает браузер, иначе фрагменты получат чужие координаты. Оригинал полотна в Commons бывает
60-мегабайтным JPEG — его телефон не откроет, поэтому оригинал мы не отдаём; если файл и так
у́же запрошенного, пишется он сам.

`iiif_base` берётся из манифеста IIIF, записанного в Wikidata свойством P6108: скрипт скачивает
манифест и достаёт адрес сервиса изображений у первого холста (поддерживаются обе версии
IIIF Presentation). Адрес вида `http://` переводится в `https://`: сайт у нас на https, и такие
тайлы браузер заблокировал бы как mixed content. Манифест не открылся или в нём нет сервиса
изображений — у картины останется один `image_url`, страница от этого работает, только зум идёт
по одному файлу. Покрытие у IIIF редкое: на 3008 записанных картин манифест нашёлся у 63 —
у «Моны Лизы» и «Ночного дозора» его в Wikidata нет.

У картин, записанных раньше, всё это дозаполняет ключ `--fill-images` (`--fill-images --all` —
перечитать у всех): имя файла берётся из `cover_url`, id Wikidata — из `external_ids`.

Координаты фрагментов и разбор машиной не заполняются — их пишет человек через админку.

### Сезоны сериалов ✅ — `scripts/catalog-import/series_seasons_tmdb.py`

Руками сезоны и серии никто не введёт, поэтому к импорту сериалов добавлен второй скрипт. Он
берёт из базы сериалы, у которых есть id TMDB (`external_ids.tmdb_tv`), и на каждый запрашивает
список сезонов (`GET /tv/{id}`), а затем каждый сезон целиком — `GET /tv/{id}/season/{n}`
отдаёт сезон вместе со всеми сериями: названия, даты, длительности и кадры. Второй запрос на
сезон в английской локали нужен ради оригинальных названий: у TMDB названия сезона и серий
локализованы, оригинала в ответе нет.

У сезона заполняются название, оригинальное название, описание, дата премьеры, постер с
размерами копии, номер, число серий, статус (все серии вышли — «завершён», иначе статус
сериала) и дата финала (самая поздняя дата среди уже вышедших серий). У серии — номер, названия,
описание, дата выхода, длительность в минутах и кадр. Размеры кадра скрипт проставляет только
с ключом `--still-sizes`: у TMDB они лежат в отдельном ответе по эпизоду, то есть стоят запроса
на каждую серию (на сотне сериалов это около десяти тысяч лишних запросов). Без них карточка
берёт обычное для кадра соотношение 16:9.

Повторный прогон безопасен: сезон пишется по детерминированному слагу «сериал-season-номер»
(вставка с разрешением конфликта), серия — по сезону и номеру. Без ключа `--refresh` уже
заведённый сезон не перезаписывается, но серии досылаются — у идущего сезона их прибавляется.
Если слаг занят чужой сущностью, сезон получает слаг с суффиксом, а прогон продолжается. Серии,
которых больше нет у TMDB, скрипт не удаляет; снять их можно через админку
(`PUT /admin/seasons/{id}/episodes`). Ключи: `--slug` — только эти сериалы, `--limit` — сколько
сериалов обойти, `--dry-run`, `-v`.

Скрипт рассчитан на заливку сотен тысяч сериалов. Загрузка и запись разведены: потоки только
качают, а в базу пишет отдельный поток пачками (`--db-batch`, по умолчанию 200 сезонов за одну
транзакцию) — очередь между ними ограничена, поэтому если база отстаёт, загрузка сама
притормаживает. Очередь задач составлена из сезонов, а не из сериалов, так что сериал с сотней
сезонов больше не занимает поток целиком. Темп задаёт ключ `--rps` (по умолчанию 45 запросов в
секунду при лимите TMDB около 50), а не число потоков `--workers`; при ответе «слишком много
запросов» все потоки выжидают указанное время, после чего темп снижается и затем
восстанавливается. Ключ `--checkpoint` ведёт файл уже залитых сериалов, поэтому прогон можно
прервать и продолжить, `--after-id` продолжает с места без файла, а Ctrl+C дописывает очередь и
выходит без потери пачки. По замеру скорость выросла с 1,7 до примерно 29 сезонов в секунду
вместе с записью серий.

Второй запрос сезона в английской локали теперь делается не всегда: если у сериала русского
перевода нет вовсе (это видно по его карточке), сезон сразу запрашивается по-английски одним
запросом — русский ответ всё равно пришёл бы английским. Это снизило цену сезона с 2,16 до 1,35
запроса. Дальше упирается уже не в нас, а в TMDB: попытка качать в 160 потоков с потолком 130
запросов в секунду дала десятую часть ответов «слишком много запросов» и скорости не прибавила.

Ключ `--worth-it` качает сезоны только тем сериалам, которым они действительно нужны: с русским
названием либо с заметной аудиторией (пороги `--min-votes` и `--min-popularity`). Сезоны ко всем
236 тысячам сериалов дампа — это около 1,2 млн сезонов и порядка десяти часов работы, причём
почти всё это бразильские и турецкие сериалы, которых никто не ищет. Принцип тот же, что у
холодного архива: русское — всё, иностранное — заметное.

Отправлять сезоны в Meilisearch после прогона не нужно — их там и не должно быть. Нужна
пересборка статики затронутых сериалов, их список скрипт печатает в конце.

### Картинки по кастам ✅ — `scripts/catalog-import/images_tmdb.py`

Скрипт добирает картинки, которые терялись при массовых заливках: импортёры сериалов и фильмов
заводили человека по имени и не сохраняли фото, которое приходило в том же ответе TMDB.

Ходит он по тайтлам, а не по людям. Один запрос карточки сериала или фильма с
`append_to_response=credits` отдаёт сразу до пятнадцати фото актёров, логотипы студий и постер,
поэтому 295 тысяч тайтлов закрывают то же, ради чего пришлось бы делать три четверти миллиона
запросов по людям. Для тех, кого нет ни в одном касте, есть режим `--mode person`.

Запись идёт только в пустые поля — фото человека, логотип студии, обложка сущности, — поэтому
прогон можно повторять сколько угодно раз. Человек ищется сначала по сохранённому TMDB id,
иначе по точному совпадению имени, и только если такое имя в базе одно: тёзка не должен
получить чужое фото. Найденной паре проставляется связь, чтобы следующие прогоны шли по id.

Полный прогон 13 ноября 2026 года: 294 866 тайтлов за два часа, 83 902 фото, 4 756 логотипов,
144 обложки, 53 329 новых связей, ни одной ошибки.

Чего добрать нельзя: обложки сезонов и кадры серий отсутствуют у самого TMDB (181 тысяча из
336 тысяч сезонов и 4,6 млн из 6,1 млн серий). Проверка режима по людям на выборке в две тысячи
дала двадцать фото — оставшиеся 597 тысяч это массовка и съёмочная группа, у которых в TMDB
фотографии просто нет.

### Картины ✅ — `scripts/catalog-import/paintings_wikidata.py`

Раздел «Картины» (`kind = painting`, миграция `20261125100000_catalog_paintings.sql`:
`ALTER TYPE entity_kind ADD VALUE 'painting'` и уникальный индекс
`entities_external_wikidata_uq` по `external_ids ->> 'wikidata'`). Источник — Wikidata и
Wikimedia Commons (решение пользователя 2026-10-30): у них есть и полотна, и художники, и музеи,
и само изображение, и русские названия.

- **Отбор** — SPARQL к WDQS: `wdt:P31 wd:Q3305213` (картина) + `wdt:P18` (изображение),
  по убыванию `wikibase:sitelinks` (число языковых разделов Википедии — прокси известности),
  порог `--min-sitelinks` (15), `--limit` (100 по умолчанию, «топ-100»). `--pool` — сколько id
  брать у Wikidata (по умолчанию `--limit * 3`): для добора окно надо раздвинуть дальше уже
  записанных, не поднимая число записываемых.
- **Весь раздел целиком — ключ `--sweep`** (14 ноября 2026). Прежний отбор «топ-N» одним
  запросом брал только верхушку: при пороге 15 языковых разделов в каталоге стояло 3 008 картин,
  тогда как в Wikidata картин с изображением около 432 тысяч, с хотя бы одним языковым
  разделом — 46 тысяч, с русским названием — 18 тысяч. Просто опустить порог нельзя: на
  десятках тысяч строк WDQS не доводит сортировку до конца и отвечает таймаутом. Поэтому обход
  идёт полосами — отдельный запрос на каждое значение числа языковых разделов сверху вниз, и
  порядок известности при этом сохраняется. Собранные полосы складываются на диск, чтобы срыв
  не стоил уже собранного, а пройденные картины отмечаются в чекпоинте. Ключ `--ru` добирает
  хвостом картины с русским названием, не дотянувшие до порога: раздел русский, и полотно из
  Третьяковки нужнее очередного провинциального портрета. Итог прогона — **47 826 картин**.
- **Темп запросов.** Лимит Викимедиа считается на клиента, а не на отдельный сервер, поэтому
  429 приходит сразу от Wikidata, Commons и Википедии. Замер показал потолок: запрос заявлений
  по 50 картинам выдерживает лишь половину запроса в секунду. Скрипт держит свой счётчик темпа
  на каждую вики, при отказе снижает темп вдвое и ждёт ровно столько, сколько просит сервер.
  Параллельность здесь вредна — она лишь быстрее приводит к отказу, поэтому этапы идут
  последовательно.
- Пачечные запросы отправляются методом POST: русское имя файла в адресе втрое длиннее, и
  пачка из пятидесяти упиралась в ограничение длины адреса.
- **Размеры картинок считаются, а не запрашиваются.** Прося у Commons копию заданной ширины,
  мы заказываем рендер каждого полотна, и ответ ждёт готовности всей пачки — на свежих файлах
  это десятки секунд. При импорте нужны только размеры, а они выводятся из размеров оригинала;
  сами копии Commons отрендерит, когда их впервые откроет читатель.
- **Ключ `--no-iiif`** отключает поход за манифестами тайлового зума в массовом прогоне: это
  десятки запросов на чужие музейные серверы ради трёх процентов попаданий, причём половина
  отвечает отказом или протухшим сертификатом. Добирается потом ключом `--fill-images`.
- **Данные** — `wbgetentities` пачками по 50 (заявления и названия), вторая пачка — названия
  того, на что картины ссылаются (художник, музей, материал, жанр, направление), описания —
  вступления статей ру-Википедии (`action=query&prop=extracts`).
- **Запись**: `title` (ру, иначе en), `original_title` (en, если отличается), `description`,
  `release_date` — год создания P571 (1 января этого года), `cover_width`/`cover_height` —
  размеры превью Commons (`imageinfo` с `iiurlwidth`, пачками по 50: `thumbwidth`/`thumbheight` —
  ровно то, что получит браузер, и приходят они только вместе с `iiprop=url`; нет миниатюры —
  размеры оригинала. Дозаполнить у уже записанных — `--fill-sizes`, перечитать у всех —
  `--fill-sizes --all`), `cover_url` — Commons
  `Special:FilePath/<файл>?width=1000` (как логотипы премий), `metadata` — `technique` (P186),
  `museum` (P195), `city` (P276, если не совпал с музеем), `height_cm`/`width_cm` (P2048/P2049 с
  переводом единиц в сантиметры), `external_ids = {"wikidata": "Q…"}`. Художник P170 — `people` +
  `entity_credits` с ролью `artist` (как режиссёр у фильма, страница человека и фильтр `person`
  работают сами). Жанр P136 → тег `kind = genre`, направление P135 → тег `kind = tag`; нет
  тега — создаётся.
- Повторный прогон безопасен: уже записанные qid пропускаются (индекс выше). После прогона —
  `scripts/reindex-search.sh`, иначе картин не будет ни в поиске, ни в разделе `/paintings`.
- Трейлеров и обложек со стороны у картин нет: `media` (`providers.rs`) для `painting` ничего не
  ищет — изображение приходит вместе с данными.
- Премии (`awards.kinds`) пока ограничены CHECK `movie|series|book|game`: вкладок «Награды» у
  картин нет.

Наполнение: `scripts/catalog-import/awards_build.py` переносит плоские `metadata.awards`
(их завёл `awards_wikidata.py` из Wikidata) в эти таблицы — премия по названию, церемония по
году, категория по `category`, номинация по работе и `won`. Крупные премии описаны в скрипте
(`CURATED`: slug, название, страна, год учреждения, `kinds`), разные названия одной премии
сводятся через `ALIASES` («Золотой лев» и «награды Венецианского кинофестиваля» — Венеция),
служебные классы Wikidata отсеивает `SKIP`; остальные заводятся автоматически (slug транслитом,
`kinds` — по типам работ), порог — `--min-records` (по умолчанию 10). На dev залито 106 премий, 2356 церемоний,
17341 номинация: 103 премии с `movie`, 13 с `series`, по одной с `book` и `game` — источник
(`awards_wikidata.py`) ходил по id TMDB, то есть только по фильмам. `season_year`, номера и даты церемоний в источнике нет — они заводятся в админке поверх залитого.

Логотипы премий (`logo_url`) проставляет `scripts/catalog-import/awards_logos.py`: элемент
премии ищется так же, берётся `P154` (логотип), `P2910` (иконка) или `P18` — последнее только
если имя файла похоже на логотип, иначе в `logo_url` попадёт репортажное фото (у «Оскара» в
`P18` красная дорожка 2009 года, у «Сезара» — портрет актрисы). Если у найденного элемента
картинки нет, смотрим его родителя: у «Золотой пальмовой ветви» логотип стоит у самого
Каннского фестиваля. Ссылка ведёт на Commons (`Special:FilePath/<файл>?width=512`), копий у
себя не держим; у премий без свободного логотипа поле остаётся пустым — фронт рисует заглушку.

Полные церемонии наливает `scripts/catalog-import/awards_ceremonies.py` — он идёт **от премии**,
а не от фильма: `awards_wikidata.py` забирал только награды, где субъект утверждения — сам фильм,
а за сценарий, режиссуру, актёрские работы и музыку в Wikidata номинируют человека (утверждение
на нём, работа — в квалификаторе P1686). Поэтому категории показывали одного победителя вместо
пяти номинантов, а `person_id` пустовал. Скрипт находит элемент премии по фильмам каталога (не
по вписанному руками QID), берёт её категории (`P361` и `P31` — у «Оскара» почти все через
`P31`), выгружает по ним все P166/P1411 с годом и работой, схлопывает строки одной номинации
(Wikidata пишет её отдельно у работы и у каждого причастного человека) и переписывает церемонию
целиком, как `PUT /admin/awards/{slug}/{year}/nominations`. Год, которого в выгрузке нет, не
трогается. Работы сопоставляются по id TMDB, люди — по имени; кого нет в каталоге, записывается
в `name`.

Фасеты Meilisearch (`catalog::awards::facets_of`): `award_slugs`, `award_years` — фильтруемые,
`award_wins`, `award_nominations` — фильтруемые и сортируемые. Через них работают
`GET /search?award=&award_year=&awarded=` и `sort=awarded`: любые выборки каталога идут только
индексом.

### `catalog_rank_kinds` ✅ — сортировка по видам (2026-11-25)

- Фильтр `person`/`role` у всех видов — термы `person:<slug>`/`role:<роль>:<slug>` поля `facet` (весь состав из

  работ брались из `entity_credits` на каждый запрос (`person_ords`, ~100 мс).

  (название, вид, описание) — из справочника `sidecar-refs.cols` (`index::refs`: отсортированные ключи и
  значения, двоичный поиск через mmap, в куче ничего). Собирается вместе со слоем Б (`reload_sidecar`, полная
  перестройка) из `studios` и `tags`.

  фильтру, а не по всему порядку.

**Скорость текстового поиска (2026-11-26).** Замер — `nexus search bench [--merge] [запросы…]` (release,
шаги как в «Проверить запрос»). Опечатки (`FuzzyTermQuery` по `title` и `people`) — только в резервном запросе
(строгий пуст): нечёткий поиск обходит словарь поля в каждом сегменте и стоил ~×10 к основному шагу. Проверки
«точное название» и «совпало в названии» (`CatalogIndex::title_sets`) — сборщиком `OrdSet` без оценок BM25 и
только среди найденных; запрос «в названии» строится из того же разбора (`TextQueries` — тройка), словарь для
автодополнения просматривается один раз. В `blend` вид и популярность совпадения считаются один раз.
Итог (1 сегмент после `--merge`, 2 млн документов): обычный запрос 1,5–6 мс, с опечаткой 9–17 мс. Перед
выкладкой на прод индекс сливается в один сегмент.

**Релевантность поиска (2026-11-25, уточнено 2026-11-26).** Работы (`EntitySidecar::rank_hits`): уровни — точное название
с ручным местом, сильное совпадение с ручным местом, совпало в названии (точное название без места — здесь же,
с долей текста 1: «мастер» — популярный «Мастер и Маргарита» выше малоизвестного фильма «Мастер») (`QueryBuilder::title_only`, второй сбор
совпадений), остальные (только люди/серия). Внутри уровня `(1 − w)·√(оценка / лучшая в группе) +
w·(балл / лучший балл вида среди найденных)`, w — `search_popularity` вида. Люди
(`PeopleSidecar::rank_hits`): `(1 − w)·√(оценка/лучшая) + w·ln(1+fame)/ln(1+max fame)`.
Популярность в слое Б — `rank_score × 10⁶` (`SortMeta::popularity`), `base_rank` — балл и дата у
всех видов (у книг прежняя формула заменена баллом вида).

## Поиск

Активные сущности индексируются в Meilisearch (индекс `entities`; скрытые — нет: правка `active`
добавляет или удаляет документ, перестройка берёт только `active`): опечатки, ранжирование, фильтры
по `kind`, тегу, году (точно или диапазоном), студии; сортировки — см. ниже. Ищется по названию,
оригинальному названию и студиям, в таком порядке важности. Клиент — тонкая обёртка над HTTP API в
`shared::search`, без SDK.

**Книги — в своём индексе Tantivy** (2026-11-17, [«Книжный поиск на Tantivy»](#книжный-поиск-на-tantivy--2026-11-17)): при заданном
`BOOKS_INDEX_DIR` запросы только про книги (`kind=book`) отвечает он, в общей выдаче книги
чередуются с работами Meilisearch. Новый параметр `GET /search` — `has_cover` (только книги),
новое поле `EntitySummary.authors` (только в книжной выдаче).

**Весь поиск на сайте — только через Meilisearch** (решение пользователя 2026-10-14): `GET /search`
и подсказки `GET /search/studios`. Публичный `GET /entities` поиска по названию не делает (`q` →
400 `use_search`); подстрока по БД (`ILIKE`) осталась только в админке `GET /admin/entities?q=`
(скрытых сущностей нет в индексе) и в `GET /people?q=` (список по алфавиту). Люди ищутся через
`GET /search/people` ([«Поиск людей»](#поиск-людей-)).

**Фильтры `GET /search`** (все через AND, `filters_of` в `search.rs`):

| Параметр | Фильтр Meilisearch | Проверка |
|---|---|---|
| `kind` | `kind = movie` | enum |
| `tag` | `tags = "<slug>"` | slug, иначе 400 |
| `year` | `year = 2001` | 1–9998; вместе с `year_from`/`year_to` — 400 |
| `year_from`, `year_to` | `year 2000 TO 2010` (включительно), одна граница — `year >= …` / `year <= …` | 1–9998; `from > to` — 400 |
| `studio` | `studios = "<название>"` — точное, без учёта регистра (так сравнивает Meilisearch), любая из студий | 1–200 символов после trim; `\` и `"` экранируются |
| `studio_slug` | `studio_slugs = "<slug>"` — студия по slug страницы `/studios/{slug}` (2026-10-15); неизвестный — пусто | slug, иначе 400 |
| `publisher` | `publishers = "<название>"` — издательство книги (`metadata.publisher`), издатель или разработчик игры (`publisher`, `developer`); точное, без учёта регистра (2026-10-30) | 1–200 символов после trim; `\` и `"` экранируются |
| `museum` | `museums = "<название>"` — музей картины (`metadata.museum`); точное, без учёта регистра (2026-10-30) | 1–200 символов после trim; `\` и `"` экранируются |
| `country` | `countries IN ["US", "GB"]` — страна производства (`metadata.countries`), ИЛИ между значениями (2026-11-06); параметр повторяемый (`country=US&country=GB`) или через запятую, разбирает `Repeated`, как `kind` | код ISO 3166-1 alpha-2, регистр не важен (`us` → `US`); неизвестный — 400 (`validate::country`) |
| `person` | `people = "<slug>"` — человек в титрах в любой роли (2026-10-15) | slug, иначе 400 |
| `person` + `role` | `credits = "<role>:<slug>"` — человек именно в этой роли | `person` — slug, `role` — `a-z`/`_`; `role` без `person` — 400 |

Сортировки поиска: без `sort` — релевантность; `recommended` / `trending` / `top_rated` —
`rank_score` / `popularity` / `quality` по убыванию; `new` — `release_ts:desc` + фильтр
`release_ts <= сегодня` (только вышедшие); `soon` — `release_ts:asc` + `release_ts > сегодня`;
`title` — `title:asc`; `random` — случайное окно выдачи (2026-11-02). Без значения поля — в конце.

**`sort=random`** — «ещё одна работа» на случай, когда ряд листания и похожие кончились. Бэкенд
делает два запроса к Meilisearch: сначала считает, сколько всего нашлось, потом берёт `limit`
карточек подряд со случайного смещения; `total` и `offset` в ответе настоящие. Раньше этим двумя
обходами занимался фронтенд. Для листания такой порядок не годится — у каждого запроса он свой,
поэтому `GET /entities/{slug}/neighbors` отвечает на `sort=random` 400.

**Соседи работы** — `GET /entities/{slug}/neighbors` с теми же параметрами, что у `GET /search`
(2026-11-02). Листание на карточке идёт по тому списку, откуда человек пришёл (страница художника,
тег, музей, поиск), и ответ `{prev, next}` — это предыдущая и следующая работа ровно того же ряда:
фильтры и сортировка передаются те же, тело запроса к индексу общее с поиском. Ряд
просматривается по одним slug'ам страницами по 1000 (всего до 5000) — тысяча коротких строк
дешевле тысячи карточек, — а найденные соседи дочитываются вторым запросом. На краях ряда —
`null`; работы в этой выдаче нет (фильтры не подходят, ряд слишком длинный, неизвестный slug) —
оба `null`, а не 404: фронтенд тогда показывает похожие. Позиции и длины ряда в ответе нет
намеренно: Meilisearch не умеет «дай номер документа в выдаче», а счётчика «14 из 142» в
интерфейсе нет.

**Подсказки студий** `GET /search/studios?q=&kind=&limit=` — facet search Meilisearch
(`POST /indexes/entities/facet-search`, `facetName: studios`): по части названия с опечатками, без
`q` — самые частые (`faceting.sortFacetValuesBy.studios = count`). Ответ
`[{name, slug, count, logo_url}]`, `name` — значение для `studio`, `slug` — страница студии и
значение для `studio_slug`, `logo_url` — логотип студии, тот же, что в `GET /studios/{slug}` и
`StudioRef` (всё из `studios` одним запросом на ответ, `studios::refs`; `null` — строки студии ещё
нет или логотипа у неё нет, 2026-10-15, логотип — 2026-11-06). В документе индекса логотипа нет:
facet search возвращает только значение фасета и счётчик, поэтому `studios` читается один раз на
ответ (а не по хиту — панель фильтров открывается одним запросом).

**Подсказки издателей** `GET /search/publishers?q=&kind=&limit=` (2026-10-30) — тот же facet search
по полю `publishers`. Ответ `[{name, count, logo_url}]`, `name` — значение для фильтра `publisher`.
`logo_url` (2026-11-06) — логотип студии с тем же названием (издатель игры часто и есть
студия-разработчик), своих логотипов у издателей и музеев нет, поэтому обычно `null`.

**Подсказки стран** `GET /search/countries?q=&kind=&limit=` (2026-11-06) — facet search по полю
`countries`. Ответ `[{code, count}]`, `code` — значение для фильтра `country` (ISO 3166-1 alpha-2);
без `q` — самые частые (`faceting.sortFacetValuesBy.countries = count`). Названия стран
(«США») показывает фронтенд (`countryName()`), в индексе только коды, поэтому `q` по названию
бессмыслен — он сопоставляется с кодом.

**Подсказки тегов** `GET /search/tags?q=&kind=&limit=` (2026-10-30) — facet search по полю `tags`:
только теги и жанры, которые есть у сущностей этого `kind` (жанры фильмов не попадают в книги).
Ответ `[{slug, name, kind, description, count}]`: в фасете только slug'и, название, `kind`
(`genre`/`tag`) и `description` дочитываются из таблицы `tags` одним запросом на ответ (тега уже
нет в БД — `description` = `null`). `q` сопоставляется со slug'ом, поэтому
фронтенд фильтрует по названию у себя, а отсюда берёт состав раздела и счётчики.

Источник правды — PostgreSQL, индекс производный:

- **После записи в админке** затронутые сущности сразу переотправляются в индекс: сама сущность,
  все сущности с изменённым тегом, все работы переименованного человека. Meilisearch применяет
  изменения асинхронно, обычно за доли секунды. Если он недоступен, запись в БД всё равно проходит,
  а в лог пишется warning.
- **Полная перестройка** без простоя, с версиями индексов: при старте приложения (в фоне), по
  расписанию и из админки — [«Перестройка поиска»](#перестройка-поиска-).
- Данные, загруженные в БД в обход API (`make seed`), попадают в индекс только после перестройки:
  `make seed` запускает её сам (`scripts/reindex-search.sh`).

**Точный `total`** (2026-10-15, `search_exact` в `search.rs`, им же пользуется `GET /search/people`):
`total` в `GET /search` и `GET /search/people` — точное число совпадений (`totalHits`), а не оценка
`estimatedTotalHits`. Точное число Meilisearch считает только в режиме `page` + `hitsPerPage`:
`offset`, кратный `limit` (фронтенд шлёт только такие), — один запрос
`page = offset / limit + 1`, `hitsPerPage = limit`; иначе выдача по `offset`/`limit` и параллельно
второй запрос счёта (`page 1`, `hitsPerPage 0`, без сортировки). Потолок счёта и листания —
`pagination.maxTotalHits = 500000` (`MAX_TOTAL_HITS`) у индексов `entities` и `people` (по умолчанию
Meilisearch считал и листал только 1000: `total` был 1000, `offset ≥ 1000` — пусто). Настройка
ставится при перестройке: после выкладки старый индекс отдаёт не больше 1000, пока не пройдёт
перестройка. Время ответа на dev (119 773 фильма) ещё не замерено.

**Оценки Nexus в индексе** (2026-10-15, `spawn_ratings_sync` / `sync_ratings` в `search.rs`).
Оценки — в `social`; сводки он присылает через `EntityRatings` в `entity_ratings` каталога (после
каждой рецензии и `replace_all` при старте). В индекс они попадают пачкой: раз в 60 с
(`RATINGS_SYNC_INTERVAL`) фоновая задача берёт `entity_ratings` с `updated_at` позже прошлого
прохода (нахлёст окна 60 с; первый проход — все сводки) и переотправляет документы этих сущностей
целиком из БД (`update_entities`: и в теневой индекс, скрытые удаляет). Выбрано вместо обновления
по событию: `social` не знает о поиске, трейт и события не меняются; задержка — до ~1 мин.
`replace_all` теперь не удаляет пропавшие сводки, а обнуляет (`count = 0`, `average = NULL`, новое
`updated_at`), чтобы обнуление дошло до индекса; для сортировок `GET /entities` это то же самое.
Повторная отправка безопасна; на нескольких инстансах каждый шлёт сам.

Если Meilisearch недоступен, `GET /search` отвечает `503`. Если индекс ещё не построен, ответ —
пустая страница. Карточки, списки, теги и справочники для `social` от Meilisearch не зависят; «Похожие»
(`/entities/{slug}/similar`) — зависят (503).

### Поиск людей ✅

Индекс `people` (2026-10-14, `people_search.rs`) — только люди хотя бы с одной работой в активной
сущности (`INDEXED_PERSON`: `person_credit_counts.active_credits > 0`, с 2026-11-14; люди без работ
в индексе не нужны, `total` честный). Документ `PersonDoc`: `id`, `slug`, `full_name`, `original_name`,
`birth_date`, `photo_url`, `known_for`, `fame` (из `person_stats`), `works_count` (работ в активных
сущностях, сезоны не считаются) и `top_works` (до 3 работ по `entity_stats.tmdb_votes`:
`{slug, title, kind, year, poster_url}`; считаются лежащим `LEFT JOIN LATERAL`). После выкладки нужна
перестройка поиска: старые документы без `works_count`/`top_works` отдаются как `0` и `[]`. Настройки: `searchableAttributes` —
`full_name`, `original_name`; `filterableAttributes` — `known_for`; `sortableAttributes` — `fame`,
`full_name`; `rankingRules` — `words, typo, proximity, attribute, sort, exactness, fame:desc`; `pagination.maxTotalHits` — 500000:
известность решает среди одинаково подходящих совпадений («Брэд» → Брэд Питт, затем Брэдли Купер,
Брэд Бёрд …), точное совпадение имени важнее славы; без `q` — по известности.

`GET /search/people?q=&known_for=&limit=&offset=` → `PeoplePage` (`items`, `total`, `limit`, `offset`,
`facets`); `PersonHit`: `id`, `slug`, `full_name`, `original_name`, `birth_date`, `photo_url`, `known_for`,
`works_count`, `top_works[]`; `fame` не отдаётся.
**`facets.known_for`** — `{роль: людей}` среди найденных по `q` без фильтра `known_for` (нулевых ролей
нет): чипы ролей на фронте. При выбранной роли `total` = `facets.known_for[роль]`.
**Микс ролей:** без `q` и `known_for` выдача — не общий рейтинг (кино перевесило бы книги и игры), а
чередование ролей по кругу: роли по убыванию числа людей, `actor` — дважды за круг; роль с
исчерпанными людьми пропускается; внутри роли порядок по `fame` (то есть по перцентилю внутри роли).
Страница `[offset, offset+limit)` раскладывается детерминированно (`mix_plan`), по роли — один запрос
к Meilisearch с `offset`/`limit`, запросы параллельно; соседние страницы не пересекаются. С `q`
порядок прежний (качество совпадения, затем `fame`). Сортировки и подборки («Именинники») не сделаны. `known_for` —
`a-z`/`_` (иначе 400), фильтр `known_for = <role>`.

Индекс строится и переключается вместе с `entities` ([«Перестройка поиска»](#перестройка-поиска-),
шаг `fill_people`, пачки по 2000). Публикация правок (`publish::run` → `search::update_index`)
пересчитывает `fame` затронутых людей (`Touched.people`: изменённый человек и состав изменённых
сущностей) и переотправляет их документы, скрытых удаляет. Фильтр `person` в `GET /search` —
по участникам в документе `entities` (см. «Участники в документе»).

Ключ в dev — `nexus_dev_master_key` (`MEILI_MASTER_KEY` в `infra/docker-compose.yml`).

**Веб-панель Meilisearch:** http://localhost:7700 (работает при `MEILI_ENV=development`). Ввести
ключ, слева выбрать индекс `entities`: пустой поиск показывает все документы, поиск работает на лету.
Индексы `entities_v<ms>` — предыдущая версия и (во время перестройки) теневая. Индексы `test_…` — остатки тестов,
упавших до очистки; на приложение не влияют, их можно удалить.

**Через curl:**

```bash
KEY='Authorization: Bearer nexus_dev_master_key'

curl -s localhost:7700/indexes -H "$KEY" | jq                                 # индексы
curl -s localhost:7700/indexes/entities/stats -H "$KEY" | jq                  # numberOfDocuments
curl -s 'localhost:7700/indexes/entities/documents?limit=20' -H "$KEY" | jq   # документы
curl -s localhost:7700/indexes/entities/documents/<uuid> -H "$KEY" | jq       # документ по id сущности
curl -s localhost:7700/indexes/entities/settings -H "$KEY" | jq               # поля поиска и фильтров
curl -s 'localhost:7700/tasks?limit=10' -H "$KEY" | jq                        # задачи, ошибки индексации
```

**Через API Nexus** — то, что увидит фронтенд: http://localhost/api/v1/catalog/search?limit=100
(пустой `q` возвращает всё, `total` — сколько документов в индексе) или вкладка «Каталог» в Swagger.

Если индекс разошёлся с БД — перестроить: `scripts/reindex-search.sh` или
`POST /admin/search/reindex` в Swagger.

## Карточки ✅

`GET /entities/{slug}` и `GET /people/{slug}` читают PostgreSQL: без кэша, без Redis и без
Meilisearch. Публичные страницы отдаёт фронтенд статикой (SSG/ISR), сюда приходят её пересборка и

## Публикация правок ✅

Код — `publish.rs`, клиент вебхука — `shared::isr`. После коммита каждой админской записи (и
`nexus media`) `publish::run` выполняет шаги по порядку:

1. **search** — документы затронутого в Meilisearch, с ожиданием применения (`search::update_index`);
   во время перестройки — и в теневой индекс.
2. **isr** — `POST {ISR_URL}/_isr/revalidate`, `Authorization: Bearer {ISR_SECRET}`,
   тело `{"paths": ["/films/dune-2021", "/people/denis-villeneuve"]}`, пачками по 100 путей.
   Пути — старые и новые адреса затронутых сущностей (`/films|series|books|games/{slug}`, как
   `KINDS` фронтенда), людей (`/people/{slug}`) и студий этих сущностей (`/studios/{slug}`). Перед
   шагами — `studios::sync` затронутых сущностей (новые студии из `metadata`).

Ошибка шага запись не отменяет и следующий шаг не останавливает: warning в лог. Meilisearch
выключен или не заданы `ISR_URL`/`ISR_SECRET` — шаг пропускается (`skipped`).

**Правка тега — в фоне** (`admin::tags::spawn_publish`, 2026-11-03). Работа пропорциональна числу
сущностей тега: у «Боевика» это 13 328 фильмов плюс их участники и связанные, и `PATCH
/admin/tags/{id}` не укладывался в таймаут шлюза (504). Теперь `publish::run` для тегов уходит в
`tokio::spawn`, ответ отдаётся сразу; упавший шаг — в логе (`tag publish finished`), индекс
подберёт перестройка, статику — следующая правка. Slug'и самих сущностей при правке тега не
меняются, адреса «до» и «после» совпадают — поэтому и сбор `Touched` идёт в фоне; при `DELETE`
список сущностей снимается до удаления (каскад чистит `entity_tags`).

Публикуется только вправду задетое: `UPDATE` возвращает `IS DISTINCT FROM` по (`slug`, `name`,
`kind`), и правка одного `description` (или присланные прежние значения) не публикует ничего —
описание тег показывает только на своей странице. В поисковых документах сущностей от тега лежит
один slug, на их страницах — название и вид (жанры в шапке).

Масштаб работы: переименование «Боевика» на деве — 13 328 сущностей, их участники (207 тысяч
человек) и статика, около 8 минут фоном; запрос при этом отвечает за 0,2 с. Отдельной блокировки
на тег нет: два переименования подряд дадут две параллельные публикации — лишняя работа, но не
расхождение (документы и страницы собираются из БД целиком).

**Поток для админки:** `PATCH /admin/entities/{id}/stream` — то же тело, что у `PATCH /admin/entities/{id}`.
Ошибки ввода (`400`, `404`, `409`) — обычный JSON до потока. Если запись прошла — `200 text/event-stream`:

```
event: plan
data: {"type":"plan","steps":[{"step":"db","title":"Сохранение в БД"},{"step":"search",...},{"step":"isr",...}]}

event: step
data: {"type":"step","step":"db","status":"done","message":"БД обновлена","duration_ms":4}

event: step
data: {"type":"step","step":"search","status":"running","message":"Обновление поиска (Meilisearch)"}

event: step
data: {"type":"step","step":"search","status":"done","message":"Meilisearch обновлён","duration_ms":61}

event: step
data: {"type":"step","step":"isr","status":"running","message":"Пересборка статики (ISR)"}

event: step
data: {"type":"step","step":"isr","status":"done","message":"Статический HTML/JSON пересобран: /films/dune-2021, ...","duration_ms":120}

event: done
data: {"type":"done","ok":true,"entity":{ ...карточка как в GET /entities/{slug}... }}
```

`status`: `running`, `done`, `skipped`, `failed`; `ok: false` — какой-то шаг упал. Схема —
`JobEvent` в `documents/api/catalog.json` (общая с перестройкой). `EventSource` не умеет PATCH и заголовки: читать
через `fetch` и `response.body`. Публикация доводится до конца, даже если вкладку закрыли. Для nginx
ответ помечен `X-Accel-Buffering: no`, иначе поток придёт одним куском.

Что затронуто, собирает `publish::Touched`: связи раскрываются сами (у сущности — её участники и
связанные произведения, у человека — его работы), а slug'и запоминаются **до** записи, поэтому удаление и смена slug пересобирают
и старые адреса.

| Запись | Что обновляется в Meilisearch и пересобирается на фронтенде |
|---|---|
| сущность: создать | она |
| сущность: изменить, удалить, теги, участники | она, все её участники (их фильмография показывает сущность) и связанные произведения (их `related` показывает сущность) |
| связь: добавить, удалить | обе сущности |
| участник: добавить, удалить | сущность и человек |
| тег: изменить, удалить | все сущности с тегом и их участники |
| человек: создать | он |
| человек: изменить (любое поле), удалить | он и все его работы (в карточке сущности есть slug, имя и фото) |
| `nexus media` (отдельный процесс) | изменённые сущности и их участники |
| `make seed` (SQL в обход API) | перестройка |

## Единый индекс каталога `catalog` (2026-11-25; заменил `books/`, `works.v*`, `people.v*`)

Один индекс Tantivy `<SEARCH_INDEX_DIR>/catalog` (`BOOKS_INDEX_DIR` больше не используется) для книг, фильмов,
сериалов, игр, картин и людей; модуль `catalog::index`. Коллекции (`collections.v*`, social) и холодный архив
(`archive/`) не тронуты. Корень `SEARCH_INDEX_DIR` обязателен (без него поиск — 503). Поколений каталогов
(`*.v<ms>`, `.current`) у `catalog` нет: перестройка — один атомарный `commit`.
- **Слой А — Tantivy**, схема `catalog-1` (файл `nexus-schema`; смена версии пересоздаёт индекс пустым).
  Поля: `kind` (STRING: `book`/`movie`/`series`/`game`/`painting`/`person`), `ord` (u64 `INDEXED | FAST`; у людей

  оригинальное имя), `title_key` (STRING: `normalize_key` названия целиком), `people` (RU_RAW, `WithFreqs`, без

  `Basic`, без fieldnorms: серия книги, студии, «известен по…» у людей), `card` (STORED: `EntitySummary` / `PersonHit`

  `catalog_entity_ords JOIN entities` (`index::search::ords_of_slugs`).

- **Запрос** `index::Query` (текст, `kinds`, `tags`, `countries`, годы, `studio`, `studio_slug`, `publisher`, `museum`,
  `award`, `award_year`, `awarded`, `person`+`role` (книги), `only_ords` (работы человека из БД для остальных видов),

  `title` берутся и сырой префикс, и его стем), опечатки (расстояние 1) только если строгий запрос пуст, точное название

  Запрос короче 3 символов не ищется только для `kinds == [book]` (у остальных видов — с первой буквы).
  Релевантность: `rank_hits` (точное название > сильные совпадения с ручным местом > оценка × (1 + ln(1+известность)/15)).
  Общий кэш ответов: ключ — поколение (отпечаток индекса + слой Б) и запрос; ряды выдачи по 1000 и более.

## Перестройка поиска ✅

**Точечная индексация** (2026-10-30): данные, залитые в БД мимо API (импорты `scripts/`,
`make seed`), доходят до поиска и без полной перестройки — `POST /admin/search/entities`
(`search::index_entities`) с телом `{"slugs": [...]}` или `{"ids": [...]}`, до 1000 за запрос.
Внутри — та же `update_entities`, что и у правки в админке: видимые переотправляются (и в теневой
индекс, если идёт перестройка), скрытые и удалённые — удаляются; ISR при этом не трогается.
Обёртка — `scripts/index-entities.sh mona-lisa guernica` (slug'и аргументами или на stdin), её
печатает импорт картин после прогона. Полная перестройка (`scripts/reindex-search.sh`) нужна
только когда индекс отстал целиком: она строит оба индекса и идёт десятки минут.

Код — `search.rs` (`reindex`), события — `jobs.rs`. Прямая очистка живого индекса не используется
никогда. Поиск всегда читает индексы `entities` и `people` — они играют роль алиасов (в Meilisearch
1.15 алиасов нет), а версии подменяют их атомарным `swap-indexes`. Оба индекса перестраиваются одной
перестройкой с общей меткой версии:

1. **create_index** — теневые `entities_v<unix ms>` и `people_v<unix ms>` с настройками; `entities`
   и `people` создаются, если их нет.
2. **fill** — все сущности из PostgreSQL пачками по 500 (keyset по `id`, карточки пачки — двумя
   запросами) в теневой индекс. Пока Meilisearch применяет пачку, читается следующая. Событие
   `progress` после каждой пачки: `{"done": 1000, "total": 100000}`.
2б. **fill_people** — `refresh_fame` всех людей, затем все люди с активной работой пачками по 2000 в
   `people_v<ms>` (`progress` со `step: fill_people`). Dev: 886 993 человека.
3. **check** — **каждый** новый индекс должен быть **не меньше `SEARCH_REINDEX_MIN_PERCENT`%** текущего
   (`numberOfDocuments`; по умолчанию и в проде — 80, 0–100, иначе приложение не стартует). Меньше —
   значит, выборка сломана или неполная: поиск не переключается, теневые индексы удаляются, ответ `409`
   (в потоке — `check: failed`). Если сущности удалены намеренно — `?force=true`. Текущий пуст —
   проверка проходит. **В dev** (`infra/docker-compose.yml`) — `0`, проверки нет: каталог часто
   перезаливается целиком (импорт из TMDB/Wikidata, откат), и перестройка при старте не должна
   упираться в старый большой индекс.
4. **swap** — `entities ⇄ entities_v<ms>` и `people ⇄ people_v<ms>` одной задачей: поиск на всех
   инстансах сразу видит новые документы, а в `*_v<ms>` остаётся предыдущая версия («на всякий
   случай»; откат — swap обратно).
5. **rotate** — хранятся строго две версии каждого: текущая и предыдущая (`*_v<ms>` только что). Все
   `entities_v*` и `people_v*` старше удаляются: «Удалены устаревшие индексы: …».
6. **isr** — `POST {ISR_URL}/_isr/revalidate` с `{"all": true}`: фронтенд отвечает `202` и
   пересобирает всю статику в фоне, поэтому шаг значит «запущено», а не «готово» (ход — в логе фронтенда). Только при
   ручном запуске; при старте и по расписанию — нет.

- **Одна за раз.** В процессе — набор идущих перестроек, между инстансами — блокировка
  `nexus:v1:catalog:reindex-running` в Redis (TTL 2 мин, работающая перестройка продлевает его каждые 30 с: убитый процесс — перезапуск, деплой — не держит блокировку дольше 2 мин; снимается в конце). Занято —
  `409` до потока. Без Redis перестраивает каждый (warning).
- **Правки во время перестройки** пишутся и в живой, и в теневой индекс, поэтому после swap не
  теряются. Ограничение: только правки на том же инстансе, где идёт перестройка.
- **По расписанию** (`SEARCH_REINDEX_INTERVAL_SECS=86400`, `0` — только при старте и вручную)
  перестраивает один инстанс: блокировка `nexus:v1:catalog:reindex-lock` на интервал.
- **Ошибка шага** — `failed` с текстом, следующие шаги не выполняются, недостроенный теневой индекс
  удаляется (не удалось — его уберёт следующая ротация).

**Поток для админки:** `POST /admin/search/reindex/stream[?force=true]` → `text/event-stream`:

```
event: plan      data: {"type":"plan","steps":[{"step":"create_index",...},{"step":"fill",...},{"step":"fill_people",...},{"step":"check",...},{"step":"swap",...},{"step":"rotate",...},{"step":"isr",...}]}
event: step      data: {"type":"step","step":"create_index","status":"done","message":"Созданы теневые индексы entities_v1759912345123, people_v1759912345123","duration_ms":35}
```

**Тесты** — `app/tests/catalog.rs`: хранятся ровно две версии, отказ переключаться при 20% и
`force=true`, ровно 80% — переключение, `SEARCH_REINDEX_MIN_PERCENT=0` — переключение без `force`

пустой запрос, латиница с опечаткой, фильтр `known_for`, правка `original_name` в админке).

## Холодный архив ✅

Двухуровневое хранение (2026-10-13, `modules/catalog/src/archive/`):

- **Горячий слой** — `entities` в PostgreSQL (полные карточки, сайт, Meilisearch): по умолчанию
  **все** фильмы с русским названием (`has_ru_locale`: в `title` есть кириллица; `DEFAULT_RU =
  usize::MAX`) и 500 самых популярных по TMDB popularity без него (`DEFAULT_FOREIGN`). До
  2026-10-14 было 90 000 + 10 000 (`--ru 90000 --foreign 10000`). Плюс то, что сборка не трогает:
  `active_manual` (промоушен, ручные), сущности без TMDB, сущности с пользовательскими данными
  (`InterestDirectory::entities_in_use`).
- **Холодный архив** — индекс Tantivy в `ARCHIVE_DIR`, через mmap (индекс не в куче процесса).
  Документ: `id` (slug; `STRING | STORED` — точный поиск и `delete_term`), `title` (`TEXT | STORED`),
  `orig_title` (`TEXT | STORED` — в ТЗ только индекс, но без него промоушен потерял бы оригинальное
  название), `type` (`STRING | STORED`), `tmdb_id` (u64), `release_date` (`YYYY-MM-DD`, хранится),
  `popularity` (f64, `FAST`), `cover_url` (URL постера TMDB `w780`, как `entities.cover_url`; только
  `STORED`; с 2026-10-14). Схема только растёт: новое поле — последнее, номера прежних не меняются,
  поэтому индекс старой схемы открывается как есть (`Index::open`; `open_or_create` требует точного
  совпадения) — постеров в нём нет и при записи они не сохраняются (`Archive::is_current`); новую
  схему даёт `build --fresh`. Токенизатор `default` (по словам, нижний регистр, без стемминга;
  «ё» ≠ «е»). Ранжирование: BM25 × `1 + ln(1+popularity)/10`.
- **Писатель** — только на время операции, бюджет ровно `WRITER_BUDGET` = 50 МБ
  (`index.writer(50_000_000)`; Tantivy делит его на ≤3 потока по ≥15 МБ). Один писатель на каталог:
  второй получает `LockBusy` → промоушен во время сборки — 409. Читатель (`OnCommitWithDelay`)
  подхватывает коммиты другого процесса сам.

**Конвейер** (`archive/pipeline.rs`, CLI вместо сервера; в dev:
`docker exec nexus-app cargo run -q -p nexus -- archive ...`, прод: `nexus archive ...`):

1. `nexus archive dump FILE.tsv` — TSV (`\t`, без кавычек; `\t`/`\n` в полях → пробел): строки
   `entities` с `external_ids.tmdb` и без `active_manual` (курсор, запись в отдельном потоке пачками по
   1000) + все документы архива. Колонки: `id`, `title`, `orig_title`, `type`, `popularity_score`
   (`entity_stats.tmdb_popularity`, нет — 0), `has_ru_locale` (`true`/`false`), `tmdb_id`,
   `release_date`, `cover_url` (`entities.cover_url` / постер документа архива). Читатель берёт колонки
   по заголовку (`tmdb_id`, `release_date`, `cover_url` — необязательные); неверные строки (slug,
   тип, число) пропускает, неверный `cover_url` (не `http(s)://`) — только обнуляет.
2. `nexus archive build FILE.tsv [--fresh] [--defer-delete] [--ru N] [--foreign 500]` (`--ru` по
   умолчанию — все):
   - проход 1 — Top-K: две min-кучи `BinaryHeap<Reverse<(popularity, slug)>>` (при равной
     popularity выше меньший slug), в памяти только 100 000 slug'ов;
   - проход 2 — чтение в блокирующем потоке, пачки по 1000 через канал (ёмкость 4). Горячая пачка —
     один `INSERT … ON CONFLICT (slug) DO UPDATE SET active = true WHERE NOT active AND NOT
     active_manual` (`unnest`); вставленные (вернулись из архива) — с `cover_url` из дампа — получают `external_ids.tmdb` и
     `entity_stats.tmdb_popularity`; из архива — `delete_term`. Холодная пачка — в архив (`delete_term` + `add_document` по slug), кроме
     `active_manual` и сущностей с данными пользователей (они остаются в PostgreSQL и убираются из
     архива);
   - `commit()` архива каждые 100 000 документов; **после** коммита строки PostgreSQL, ушедшие в
     архив, удаляются пачками по 1000 (одна транзакция на пачку: повторная проверка
     `entities_in_use`, `DELETE FROM entities` — каскадом титры, теги, статистика,
     связки импорта; затем люди без единой работы). Падение посреди сборки оставляет согласованное
     состояние: удалено только то, что уже в архиве; повтор dump + build доводит до конца;
   - `--fresh` — архив пересоздаётся пустым в **текущей схеме** (`Archive::recreate`: под писателем
     удаляются файлы индекса, кроме `.tantivy-*.lock`, затем `Index::create`; дамп уже содержит
     архив). Сервер, открывший индекс раньше, подхватывает новый на коммите и читает постеры сразу
     (номера полей прежние); между пересозданием и первым коммитом (100 000) поиск по архиву пуст;
   - в конце — перестройка Meilisearch с `force` и ISR `{"all": true}`.
   Отчёт: `rows`, `invalid`, `hot` (`inserted`, `activated`), `archived`, `deleted`,
   `kept_in_use`, `kept_manual`, `people_deleted`, `archive_size`, `manual_archived` (строк, не
   допущенных в Top-K: документы архива с `manual`, их проход 1 пропускает). Ручной набор читается из архива до
   `--fresh`, флаг `manual` сохраняется; id архивных фильмов в PostgreSQL не пишутся.
3. Место на диске PostgreSQL возвращает только `VACUUM FULL` (блокирует таблицы — окно
   обслуживания): `entities`, `entity_credits`, `people`, `person_credit_counts`, `entity_stats`,
   `entity_tags`, `catalog_import.movies`, `catalog_import.people`.

**Первичная раскладка (миллион строк)** — построчное удаление упирается в FK-каскады и триггер
счётчиков на каждый титр со случайным чтением диска (на dev ~32 строки/с, ~9 ч). Поэтому:
`nexus archive build FILE --fresh --defer-delete` (архив, строки остаются, поиск не
перестраивается) → `scripts/archive-purge.sql` (перед файлом в той же сессии — временная таблица
`archive_ids(tmdb_id)`, заполненная из `nexus archive ids` через `COPY FROM STDIN`; одна транзакция: `session_replication_role =
replica` — нужен суперпользователь, `LOCK … EXCLUSIVE` на `entities`/`people` — чтение идёт,
set-based удаление детей, `entities`, людей без работ (кроме нужных пользователям —
`InterestDirectory::people_in_use`: в интересах или с комнатой чата; `delete_entities`), пересчёт `person_credit_counts` и
`tags.entities_count` как в миграции `entity_active`, проверка всех FK на `entities`/`people` —
висячие → ROLLBACK; повторный запуск ничего не находит) → `VACUUM FULL` → перестройка поиска
(`POST /admin/search/reindex?force=true` или перезапуск). Тест — `deferred_delete_and_purge_script`.

**Ручной перенос в архив** (2026-10-14, `archive::demote`): `POST /admin/archive/demote`
`{"slugs": [...]}` (1–100, без повторов). Пропускаются с причиной (`skipped[].reason`): `not_found`
(нет на сайте), `no_tmdb` (без `external_ids.tmdb`: пометку `manual` держит документ с TMDB id), `in_use` (данные
пользователей — `InterestDirectory::entities_in_use`, как в сборке; решение пользователя: не
удалять их). Остальные: `Touched::collect` (адреса страниц, участники) → писатель архива (занят —
409, ничего не меняется) → `upsert` документов (название, оригинальное название, дата, постер, TMDB
id, popularity, `manual = true`) и `commit` → одна транзакция:
`pipeline::delete_entities` (`entities` вместе с `active_manual` — каскадом титры, теги,
статистика; люди без других работ) → упала БД — документы удаляются из архива обратно →
`publish::run` (удаление из Meilisearch, `fame` участников, ISR). Ответ `{archived, skipped}`.
Возврат — промоушен «скелетом» (описание, титры, жанры теряются). Тест —
`demote_moves_films_to_archive_and_build_keeps_them_cold`.

**Повторная сборка** (новые popularity после «Обновить рейтинги»): `dump` + `build` без `--fresh` —
фильмы архива участвуют в Top-K наравне, поднявшиеся возвращаются в PostgreSQL «скелетом».
Ограничения: возвращённый **сборкой** фильм — «скелетом», без описания, титров и жанров (постер —
из архива, если есть; дозаливка — `tmdb_full.py`). Промоушен и возврат открытием страницы берут
полные данные TMDB ([«Возврат из архива открытием страницы»](#возврат-из-архива-открытием-страницы-)).
«Пересобрать активные» работает только по горячему слою.

### Возврат из архива открытием страницы ✅

Решение пользователя (2026-10-15): кто-то открыл фильм в архиве — значит, ему место на сайте.
Фронтенд показывает архивную страницу (`GET /archive/entities/{slug}`) и сразу шлёт
`POST /archive/entities/{slug}/restore` (публичный): бэкенд за ~1–2 с берёт всё из TMDB, возвращает
фильм на сайт и отвечает **полной карточкой** (`EntityDetail`, как `GET /entities/{slug}`) —
фронтенд подменяет страницу. Код — `archive::restore`, раскладка TMDB — `archive/enrich.rs`.

1. slug неверный — 404; фильм уже на сайте (`active`) — 200 и карточка (второй посетитель,
   параллельный запрос: запросы одного slug в процессе идут по очереди, `IN_FLIGHT`).
2. Документа в архиве нет — 404; не фильм или без TMDB id — 409 `not_restorable`;
   документ архива с `manual` (убран админом) — 409 `kept_in_archive`.
3. Нет `TMDB_API_KEY` или `ARCHIVE_RESTORE_PER_HOUR = 0` — 503 `restore_unavailable`. Лимит
   возвратов в час (`ARCHIVE_RESTORE_PER_HOUR`, по умолчанию 300, `governor`, на процесс и каталог
   архива) — 429 с `Retry-After`: боты не вытащат архив на сайт.
4. `GET {TMDB_API_URL}/movie/{id}?language=ru-RU&append_to_response=credits,release_dates,keywords,
   translations,alternative_titles,images,videos,external_ids,watch/providers,recommendations,
   similar,reviews,lists` (таймаут 8 с). Сеть/5xx/429/401 — 503 `tmdb_unavailable`, фильм остаётся в
   архиве; 404 (фильма в TMDB нет) — возврат «скелетом» из документа архива.
5. Одна транзакция (`enrich::insert_film`, правила полей — как `tmdb_full.py`): `entities`
   (`active`, `active_manual`; название — русское из TMDB, нет перевода — из архива; оригинальное,
   описание, дата, постер `w780`; `metadata`: `runtime_min`, `countries`, `studios`, `age_rating` RU
   иначе US, `trailers` — YouTube, официальные и русские первыми, до 5; `external_ids.tmdb` — в
   том же `INSERT`), `entity_stats` (`imdb_id`, `tmdb_popularity`, `tmdb_votes`), студии
   (`studios::sync` с компаниями из ответа TMDB), жанры → теги `genre` (slug как `GENRE_SLUGS`; нет тега — создаётся),
   титры: режиссёры, сценаристы, продюсеры, композиторы, операторы, монтажёры, весь актёрский
   состав по `order`; позиции — по ролям. Люди — по TMDB id в `catalog_import.people`, новые
   создаются (slug — транслит имени, `enrich::slugify` = `slugify` из `import_tmdb.py`; занят —
   `<slug>-<tmdb_id>`; фото `h632`). Конфликт уникальности (вернул другой инстанс) — 200 и его
   карточка.
6. Документ удаляется из архива, если писатель свободен (идёт сборка — останется до неё:
   `active_manual` → `keep`).
7. Публикация в фоне (`tokio::spawn`): Meilisearch, `fame` участников, ISR — статическая страница
   генерируется; ответ не ждёт.

Не делается: сиквелы по коллекциям TMDB (сырьё не хранится), рейтинг IMDb (придёт с
«Обновить рейтинги»). Админский промоушен — тот же `insert_film`: с ключом — полные данные, TMDB
недоступен — «скелетом» (warning). Тест — `restore_on_open_brings_the_full_film_back`
(подставной TMDB: полный фильм, 404 → «скелет», 500 → 503, повтор, лимит, `kept_in_archive`).

## Книги из LibGen ✅

`nexus books import --dump FILE.sql[.gz] [--table updated|fiction] [--batch-size 2000] [--limit N]`
(`catalog::books`, CLI — `app/src/main.rs`; dev: `docker exec nexus-app cargo run -q -p nexus -- books import ...`).
Метаданные русских книг из официального SQL-дампа LibGen (`libgen.sql` → таблица `updated`,
`fiction.sql` → `fiction`); файлы не скачиваются.

- Чтение потоковое (`books::dump::Statements`: операторы по `;` вне строк и комментариев, в памяти
  один `INSERT`), `.gz` — `MultiGzDecoder`; разбор файла — в `spawn_blocking`, запись — пачками,
  каждая в своей транзакции (прерванный импорт продолжается повторным запуском).
- Колонки — по `CREATE TABLE` из дампа или списку колонок `INSERT`; без них — порядок `updated`
  (`books::UPDATED_COLUMNS`). Обязательные: `Title`, `Language`, `MD5`.
- Отбор: `Language` содержит `ru`/`rus`/`Russian`/`Русский` (и в списке `Russian, English`),
  `Visible` пустой, md5 — 32 hex, название непустое. `--limit` — по отобранным строкам.
- Книга (`entities`, `kind = 'book'`, `active = true`): `title` (≤ 300), `release_date` = 1 января
  года (первые 4 цифры `Year`, 1000–2100, иначе `NULL`), `cover_url` = `https://libgen.is/covers/`
  + `Coverurl` (абсолютный URL — как есть), `metadata` через `metadata::validate` (`pages` — ведущие
  цифры `Pages`, `publisher`, `isbn` — первый корректный из `Identifier`; невалидное отбрасывается).
  slug — `slugify(title)` (≤ 80), занят — `-<fnv8(work_key)>`, без букв — `book-<hash>`.
- Всё о книге — в `entities`: md5, формат и `ID` файла — `metadata.libgen.files`, ключ произведения
  (нормализованные название и авторы, `Book::work_key`) — `metadata.libgen.work`. Файлы одного
  произведения — одна книга; карточку задаёт первый файл, следующие (в том числе при повторном
  импорте) дописываются в `files` (до 200). Известные md5 пропускаются; остальные поля созданной
  карточки импорт не меняет.
- Авторы — `people` (`full_name`, slug как у книги, без букв — `author-<hash>`) + `entity_credits`
  (`role = 'author'`, `position` — порядок в `Author`, до 5). `Author` делится по `,`/`;`;
  «Фамилия, Имя Отчество» и «Фамилия, И.О.» — один автор. Тот же автор в следующих книгах —
  человек с тем же именем (`replace(lower(full_name), 'ё', 'е')`), уже записанный автором
  (`role = 'author'`); актёры и режиссёры TMDB с таким именем не подхватываются.
- Событий нет (как у `nexus archive`). Если поиск включён и книги созданы — `search::reindex`
  (`force: false`, `revalidate: true`): книги и авторы попадают в Meilisearch.
- Отчёт: строки дампа, русские, известные, книги, файлы, люди, титры.
- Второй источник — Google Books API: `scripts/books-import/google_books.py` (`requests`,
  `psycopg2`; `DATABASE_URL`, `GOOGLE_BOOKS_API_KEY`). Запросы `subject:`/`inauthor:` (пример —
  `DEFAULT_QUERIES`), `langRestrict=ru` и `volumeInfo.language == 'ru'`, страницы по 40
  (`startIndex`), пауза `--delay`, повторы на 429/5xx. Пишет те же `entities` (`kind = 'book'`:
  `title`, `description` без HTML, `release_date`, `cover_url` — первая настоящая обложка из
  кандидатов: Google `books/content?vid=ISBN…&zoom=1` (быстро; только JPEG, не заглушка —
  `GOOGLE_PLACEHOLDERS`), `imageLinks`, Open Library `/b/id/` (через archive.org, секунды),
  Open Library `/b/isbn/…?default=false`; ни одной — `NULL`; `metadata` `isbn`/`pages`/`publisher`) и
  авторов (`people` + `entity_credits`, поиск как выше). Без `metadata.libgen`. Дубликат — книга с
  тем же `metadata.isbn` (`@>`, GIN `entities_metadata_gin`), в том числе из LibGen; без ISBN —
  пропуск. Источник `--source google|openlibrary` (Open Library — без ключа: `search.json`,
  `language=rus`, название кириллицей, ISBN сначала 978-5…, переводчики-латиница отбрасываются, если
  есть автор кириллицей), `--limit N`. `--fix-covers` — заново выбрать обложку у записанных книг с
  ISBN без обложки или с обложкой Open Library (найти не удалось — старая остаётся; поиск
  Google Books API по `isbn:` с ключом; Open Library — одна попытка, 10 с).
  `--require-cover` — книги без обложки не записываются. Ключ — `GOOGLE_BOOKS_API_KEY` из
  окружения или строки `infra/.env`. Затем `scripts/reindex-search.sh`.
- Обложки книг — через кэш nginx (`infra/nginx.conf`, `infra/covers_cache.conf`, том
  `coverscache`, до 2 ГБ, 90 дней): `cover_url = {PUBLIC_URL}/covers/ol/...` →
  `https://covers.openlibrary.org/...` (два перенаправления на archive.org проходит nginx —
  `recursive_error_pages`), `{PUBLIC_URL}/covers/google/...` → `https://books.google.com/...`.
  Хосты — переменными (недоступный источник не мешает старту gateway); `proxy_cache_lock`,
  `proxy_cache_use_stale` при ошибках источника; ответ — `X-Cache-Status`, `Cache-Control:
  public, max-age=2592000`. Скрипт проверяет кандидатов сразу через кэш (проверка = прогрев);
  `--proxy-covers` переводит уже записанные внешние ссылки на кэш и прогревает его (замер:
  первая загрузка 1,15 с в среднем, из кэша — 0,00 с). Ссылка абсолютная — её принимает
  `validate::url` в админке.

Тесты: `app/tests/books.rs` — `imports_russian_books_with_authors_and_is_idempotent`,
`limit_and_dump_without_schema`; разбор дампа и полей — модульные тесты `books::dump`, `books`.

## Книги из библиотеки Cassandra ✅ (2026-11-17)

`nexus books cassandra DIR [--batch-size 1000] [--limit N]` (`catalog::books::cassandra`; dev:
`docker compose run --rm --no-deps -v /path/to/library/data:/import:ro app /target/debug/nexus books cassandra /import`).
Библиотека — каталог настольного приложения Cassandra: `metadata/*.jsonl` (книга на строку) и
`covers/` (в старых библиотеках `convers/`; обложки AVIF `<пачка>/<id>.avif`).

Что пишется (миграция `20261208100000_catalog_books_cassandra.sql` — только индексы, своих таблиц нет):

- `entities` (`kind = 'book'`): `title` (до 300 символов), аннотация → `description` (до 20 000
  символов, длиннее — обрезается), год издания (или год написания, если издания нет) →
  `release_date` (1 января), `cover_url` / `cover_width` / `cover_height`, `metadata` — `isbn`
  (с проверкой контрольной цифры; невалидный отбрасывается, книга остаётся), `publisher`,
  `series`, `series_number`, `language`, `original_language`, `keywords`, `written`, `words`,
  `file`; `external_ids.cassandra` — номер книги в библиотеке (уникальный индекс
  `entities_external_cassandra_uq`).
- Slug: `sobache-serdtse` → `sobache-serdtse-bulgakov` (фамилия первого автора) →
  `sobache-serdtse-<fnv1a32 от "cassandra:<id>">`; без кириллицы и латиницы — `book-<hash>`.
- Люди: авторы (`role = 'author'`, до 10) и переводчики (`role = 'translator'`, до 5) —
  `people` + `entity_credits`, `position` сквозной (сначала авторы). Человек ищется по имени
  (`replace(lower(full_name), 'ё', 'е')`) среди тех, у кого уже есть работа автором или
  переводчиком; иначе создаётся (`slug` из имени, занят — с хешем). «Неизвестен автор» и
  подобные не заводятся.
- Жанры: коды FB2 (`sf_fantasy`) → русские названия по таблице `books::genres::GENRES`
  (219 названий) → теги `tags.kind = 'genre'` + `entity_tags` (до 8 на книгу). Тег с таким
  названием уже есть (жанр фильмов «Фэнтези», «Ужасы») — книга получает его же; кода нет в
  таблице — жанр пропускается.
- Обложки: файл копируется в `BOOK_COVERS_DIR/<пачка>/<id>.avif` (через временный файл; уже
  лежит такой же — не копируется), размеры читаются из бокса `ispe`; `cover_url` =
  `{PUBLIC_URL}/covers/books/<пачка>/<id>.avif`, раздаёт gateway (`infra/nginx.conf`, том
  `archivedata` смонтирован в nginx только для чтения). `BOOK_COVERS_DIR` не задан — книги без
  обложек. Замена обложки — `POST /admin/entities/{id}/cover` (тот же путь, файл подменяется);
  поэтому gateway отдаёт `/covers/books/` с `Cache-Control: public, max-age=86400` (было
  `max-age=31536000, immutable`): новая обложка видна браузерам не позже чем через сутки.
- Не переносятся: оглавление, программа, версия и дата документа, город, ID FB2, источник, OCR.

Повторный запуск: книга с известным `external_ids.cassandra` пропускается целиком (её могли
править в админке). Пачка — одна транзакция; прерванный импорт продолжается повторным запуском.
После импорта: `nexus books index` (книжный индекс) и `POST /admin/search/reindex` (новые люди
в индексе людей Meilisearch). Замер (dev, 417 161 книга): ≈5 с на 1000 книг.

Тесты: модульные `books::cassandra` (разбор строки, slug'и, размеры AVIF, языки, путь обложки),
`books::genres`.

## Читалка книг ✅ (2026-11-22)

`GET /api/v1/catalog/books/{slug}/epub` (`books/reader.rs`, гость или пользователь) отдаёт EPUB
книги для читалки на фронте (foliate-js/epub.js); скачивание добавим позже (`Content-Disposition`).

- **Где файл:** `metadata.file = {archive, path, size}` (пишет `nexus books cassandra`). Архивы
  `<от>-<до>.arx` (Jubako, zstd) лежат в `BOOKS_ARCHIVES_DIR` (`Config::books_archives_dir`; dev —
  `/srv/book-archives`, смонтирован только для чтения из `BOOKS_ARCHIVES_HOST`, по умолчанию
  `/home/dev/cassandra.books/data/archives`; на сервере — HDD). Запись достаётся крейтом `libarx`
  0.4.2 (`ExtractBuilder` одной записи, `spawn_blocking`), без внешней программы `arx`.
- **Кэш:** извлечённый файл — в `BOOKS_EPUB_CACHE_DIR/<архив без .arx>/<path>` (по умолчанию
  `<tmp>/nexus-epub`, dev — `/var/lib/nexus/epub-cache`); попадание обновляет mtime, после
  каждого извлечения удаляются самые старые файлы, пока кэш больше `BOOKS_EPUB_CACHE_MB` (2048).
  Извлечение идёт во временный `.tmp-<uuid>` и переименовывается — параллельные запросы не видят
  недописанный файл.
- **Доступ:** `metadata.public_read = true` (ставит админ правкой метаданных книги) — всем, иначе
  только ролям `vip` и `admin` (`Role::can_read_books`, не по старшинству: `author` не читает).
  Гость → 401, другая роль → 403.
- **Ответ:** 200 `application/epub+zip`, `Content-Disposition: inline`, `Cache-Control:
  private, max-age=3600` (публичная — `public, max-age=86400`). 404 — нет книги, нет
  `metadata.file`, недопустимый путь (`..`, `/`, архив не `.arx`) или запись не извлеклась;
  503 — `BOOKS_ARCHIVES_DIR` не задан или файла архива нет.
- **Кэш в браузере (2026-11-22):** публичные книги фронт хранит в IndexedDB; закрытые — с
  проверкой `HEAD /books/{slug}/epub` перед каждым открытием (только доступ и `metadata.file`,
  архив не читается: 200 / 401 / 403 / 404, `Cache-Control: no-store`; 401/403 → копию удалить)
  и автоудалением через 30 дней. В профиле — «Сохранено на устройстве» и «Очистить».
- **Статичная страница на CDN** одна для всех: кнопку «Читать» показывает JS по `metadata.file`,
  `metadata.public_read` и роли из токена; гостю на закрытой книге — «Войдите», `user` — «Доступ
  по приглашению». Файл защищает только этот эндпоинт.

## Книжный поиск на Tantivy ✅ (2026-11-17)

Книги (`kind = 'book'`) ищутся в собственном индексе Tantivy, а не в Meilisearch
(`catalog::books::{index,sync,search}`). Включается каталогом `BOOKS_INDEX_DIR`
(`Config::books_index_dir`; dev/prod — `/var/lib/nexus/books-index` в томе `archivedata`);
пустое значение возвращает книги в Meilisearch (после `POST /admin/search/reindex`). Остальные
разделы остаются в Meilisearch.

**Маршрутизация** (`books::search::routed`, `search::books_query`, `search::blended`):

- `GET /search?kind=book`, `GET /entities/{slug}/neighbors?kind=book`, похожие книги
  (`GET /entities/{slug}/similar`), `GET /search/tags?kind=book`,
  `GET /search/publishers?kind=book` — отвечает Tantivy. Параметры и ответы те же.
- Запрос без `kind` или `kind=book` вместе с другими типами — общая выдача: работы Meilisearch
  и книги чередуются («две работы — книга», пока есть обе стороны; оценки двух движков
  несравнимы), `total` — сумма. `sort=random`, фильтры, которых у книг не бывает, или книг под
  запрос нет — отвечает один Meilisearch.
- В индекс Meilisearch книги при включённом книжном поиске не попадают
  (`books::search::in_meili`: `e.kind NOT IN ('season', 'book')` в перестройке и досылке).

**Отличия от Meilisearch для книг:** `q` ищет по названию, оригинальному названию, авторам и
серии; в `EntitySummary` есть `authors: [{slug, name}]` (только в книжной выдаче); работает
фильтр `has_cover=true|false`; фильтр `book_form` (2026-11-22) — вид текста через запятую:
`book`, `collection` (сборник, `metadata.collection`), `article` / `document`
(`metadata.kind`), или `all`; **по умолчанию `book`** — сборники, статьи и документы в обычной
выдаче, «похожих» и соседях не показываются; неизвестное значение — 400 (`filters_of`); в
Meilisearch-пути игнорируется. В слое Б — фасеты `form:<вид>` (`sidecar::form_key`), у каждой
книги ровно один (`BookDoc.form`, `BookForm`; SQL `sync::COLUMNS`: `kind` article/document →
он, иначе есть `collection` → `collection`, иначе `book`); `BookQuery.forms` пусто = только
книги; `sort=trending` = `popular`, `sort=awarded` = `recommended`
(статистики TMDB и наград у книг нет); фильтры `studio`, `studio_slug`, `museum`, `country`,
`award`, `award_year`, `awarded=true` дают пустую выдачу; `GET /search/tags?kind=book` отдаёт до
300 тегов (жанров FB2 больше двухсот), `q` там игнорируется, как и раньше.

**Как ищет** (логика перенесена из настольной библиотеки Cassandra, `index/query.rs`):

- слова запроса — через И, поля одного слова (название, автор, серия) — через ИЛИ; до 16 слов,
  до 200 символов;
- анализатор `ru_stem`: слова, нижний регистр, `ё` → `е`, русский стеммер; токены длиннее 80
  байт отбрасываются;
- автодополнение последнего слова, если запрос не кончается пробелом или знаком: единственное
  слово — от 3 букв, при нескольких словах — от первой. Слово раскрывается по словарю
  `title_raw` / `author_raw` в ИЛИ не более 64 самых частых слов (просмотр не дальше 4000 слов на
  сегмент) — цена запроса ограничена при любом префиксе; edge n-gram и `RegexQuery` не
  используются;
- опечатка в имени автора (одна правка, слова от 4 букв) — всегда; опечатка в названии — только
  если строгий запрос ничего не нашёл (резервный запрос: одна правка в одном слове);
- веса: точное название целиком (12, для одного слова — 4) > точное имя автора (6) > точная
  фраза (4) > слово в названии (2) > автодополнение (1,5) > слово в имени автора (1) > серия
  (0,8) > опечатка (0,5 / 0,3);
- релевантность умножается на известность автора: `1 + ln(1 + работ у автора) / 15`
  (`person_credit_counts.active_credits`, максимум по авторам книги) — из книг с одинаковым
  названием первой встаёт книга известного автора.

**Два слоя** (2026-11-18, `index/query.rs` + `index/sidecar.rs`): Tantivy (слой А) держит только
редко меняющееся — текст для поиска, карточку и номер книги; фасеты, сортировки и ручной порядок —
в слое Б в RAM (`ArcSwap<Sidecar>`), он собирается из PostgreSQL и подменяется атомарно, не трогая
индекс. **Запрос в PostgreSQL не ходит:** без текста Tantivy не вызывается вовсе (битовые маски
фасетов + готовый порядок), с текстом Tantivy отдаёт пары (номер, оценка), порядок строит слой Б.

**Что в индексе** (схема `books-4`, файл `nexus-schema` рядом с индексом; другая версия — индекс
пересоздаётся пустым и строится заново): `id` (uuid-терм, `delete_term`), `slug` (терм + колонка),
`card` — хранимая строка выдачи в JSON (`id`, `slug`, `title`, `original_title`, `release_date`,
`cover_url`, размеры обложки, `authors`; выдача без похода в PostgreSQL), текст `title` /
`title_raw` / `title_key`, `author` / `author_raw` / `author_key`, `series`, и `ord` (u64-колонка,
номер книги из `catalog_entity_ords`). Аннотации в индексе нет — карточка книги читается из БД
(`GET /entities/{slug}`) и раздаётся фронтендом как статическая страница. Фильтровых и
сортировочных полей в индексе больше нет (`tags`, `credits`, `publisher*`, `language`,
`has_cover`, `year`, `release_day*`, `popularity`, `sort_*` удалены в `books-4`).

**Слой Б** (`books::sidecar::Sidecar`, всё индексировано номером книги `ord: u32`):

- `SortMeta` — 8 байт на книгу (`manual_rank: u16`, `flags: u16` — обложка / аннотация / автор,
  `popularity: u32` — работ у самого плодовитого автора): 300 000 книг = 2,4 МБ;
- фасеты — `RoaringBitmap` на значение: `tag:<slug>`, `person:<slug>`, `role:<role>:<slug>`,
  `pub:<ключ издательства>`, `lang:<код>`, годы (`BTreeMap<i32, RoaringBitmap>`), обложка, все
  видимые книги; фильтры запроса — пересечение масок (`any_tags` — объединение, «кроме» — снятие
  битов; slug → номер через терм `slug` и колонку `ord`);
- готовые порядки (`Vec<u32>` + обратные позиции): «Рекомендуемые» (сначала ручные места по
  возрастанию, затем балл `BookDoc::rank`), `new` (по дате), `title`, `popular`, `rating`; узкий
  фильтр (`|фильтр| × 16 < книг`) сортируется по позициям, широкий — проходом по порядку;
- подсказки (теги и издательства со счётчиками) — готовые списки;
- поколение (`generation`) — часть ключа кэша выдачи: подмена слоя Б сбрасывает кэш сама.

Снимок слоя Б пишется на диск (`<SEARCH_INDEX_DIR>/catalog/sidecar-entities.bin`, формат `NXSIDE02` — с 2026-11-22 фасеты `form:*`; снимок `NXSIDE01` не читается и пересобирается из БД, атомарно через
`.tmp` + rename) при каждой подмене и читается при открытии индекса: сервер после рестарта и бенч
`nexus books load` работают без похода в БД.

**Ручной порядок** (`catalog_manual_ranks`, `SortMeta::manual_rank`): место `1..=65535` в общем
списке книг, `0` — нет места. Ранг глобальный: внутри фасета книги сохраняют относительный порядок
(третья книга списка — первая в жанре, если первые две не из него). С текстом (`sort` не задан)
порядок совпадений: (1) точное название запроса (`title_key`) — по месту, затем по оценке;
(2) сильные совпадения (оценка × известность ≥ 50 % лучшей, `STRONG_SHARE`) с местом — по месту;
(3) остальное — по оценке × `1 + ln(1 + работ у автора) / 15`. Слабое совпадение (опечатка, слово
серии) ручное место не поднимает. С текстом и явной сортировкой — совпадения в готовом порядке
этой сортировки. Источник списка — файл `Название — Автор` (`nexus books ranks FILE`) или
`PUT /admin/books/ranks`.

**Сборщик совпадений** `OrdHits` (свой `Collector` Tantivy): читает колонку `ord` и сразу
отбрасывает книги не из маски фильтра — узкий фасет при широком запросе не теряет совпадений
(фильтр не после «лучших N»), `total` — точное число совпадений. Номер → адрес документа
(`TextMap`, 8 байт на книгу) строится заново на каждое состояние индекса (отпечаток сегментов) и
пересекается с фильтром (`indexed`): книга, которую слой Б знает, а текст ещё не записан, не даёт
пустой строки выдачи.

**Сортировки:** без `sort` и с текстом — релевантность с ручными местами (выше); без текста,
`recommended` — ручные места, затем балл (число оценок Nexus, затем обложка / аннотация / автор,
затем известность автора, затем год); `new` — только вышедшие, по дате; `soon` — только не
вышедшие; `title` — по первым 9 знакам ключа названия; `popular` — число оценок Nexus; `rating`
(и `top_rated`) — средняя оценка Nexus. При равных ключах — по номеру книги. `total` точный,
`offset` до 100 000.

**Подсказки** — из слоя Б: теги и издательства со счётчиками видимых книг. Издательства — по
части названия без учёта регистра и `ё`, сначала начинающиеся с неё. `CatalogIndex::facet_counts`
(счётчики значений фасета среди книг под запрос) — есть в индексе, в HTTP пока не выведен.

**Кэш:** до 512 ответов поиска (страницы до 100 карточек) и 256 рядов выдачи (номера книг) в
памяти процесса; ключ — запрос, `limit`, `offset` и поколение = отпечаток сегментов индекса ×
поколение слоя Б; сбрасывается сам при коммите в индекс и при подмене слоя Б.

**Синхронизация** (`index/sync.rs`):

- Номер книги — `catalog_book_ords.ord` (identity с 0): выдаётся при первом чтении книги
  (`INSERT … WHERE NOT EXISTS` — номера не тратятся на уже известные книги), не меняется.
- `nexus books index` — полная перестройка из БД: видимые книги пачками по 2000 (keyset по `id`,
  индекс `entities_book_id_idx`), один коммит — до него поиск читает прежний индекс; тем же
  проходом собирается и подменяется слой Б, в `catalog_book_ords.text_hash` пишутся отпечатки.
  Писатель — 50 МБ, один поток. Замер (dev, отладочная сборка): ≈50 000 книг в минуту.
- `nexus books sidecar` / `POST /admin/books/sidecar` / раз в сутки — только слой Б (тот же
  проход по БД, без записи в Tantivy) + снимок на диск.
- Сервер при старте: индекс пуст — строит его в фоне (и слой Б); индекс есть, снимка слоя Б нет —
  собирает слой Б; до конца сборки книжная выдача пуста. Дальше фоновая задача
  (`sync::spawn_initial` → `sidecar_loop`): пересборка слоя Б после правок не чаще раза в 30 с
  (`SIDECAR_MIN_INTERVAL`) и раз в сутки (`SIDECAR_DAILY`); раз в минуту (`RANKS_POLL`) сверяет
  отпечаток `catalog_manual_ranks` (`count`, `max(updated_at)`) и при изменении применяет только
  места (`Sidecar::with_ranks`: фасеты и прочие порядки не пересобираются — миллисекунды).
- Правка книги в админке, `POST /admin/search/entities` и новые оценки Nexus
  (`search::sync_ratings`) — `sync::update` из `search::update_entities`: в Tantivy пишутся только
  книги, у которых изменился отпечаток текста (`BookDoc::text_hash`, FNV-1a по карточке, серии и
  номеру; хранится в `catalog_book_ords.text_hash`); скрытые и удалённые — удаляются из индекса
  сразу (отпечаток → `NULL`); новые оценки, теги, места — только в слой Б (фоновая пересборка).
  Писатель один на каталог: пока идёт перестройка, досылка получает `Busy` (в лог).
- Читатель следит за коммитами сам (`ReloadPolicy::OnCommitWithDelay`), поэтому перестройку
  можно запускать отдельным процессом при работающем сервере; слой Б другого процесса сервер
  подхватит своей пересборкой (места — опросом).

`nexus books search QUERY` — запрос к индексу из терминала: всего найдено, время холодного
запроса и повтора из кэша, первые 10 книг. `nexus books ranks FILE` — ручной список из файла
(`books::ranks`, см. «Ручной порядок книг»).

**Издания книг** (2026-11-18): дубль книги — та же `entities` (`kind = 'book'`) с `parent_id` основной
книги (как сезон у сериала, `GET /entities/{slug}/seasons` отдаёт издания). Издания не попадают в
книжный поиск, слой Б и сопоставление ручного списка (`e.parent_id IS NULL` в `books::sync` и
`books::ranks`); при досылке книга, ставшая изданием, удаляется из Tantivy. Расставляет
`scripts/catalog-import/books_llm.py apply` (основная — с обложкой и бо́льшим файлом).

## Ручной порядок книг ✅ (2026-11-18)

`nexus books ranks FILE` (`books::ranks::import`): файл `Название — Автор1, Автор2` (как
`knigi_10_000_progress.txt`; заголовок, пустые строки и `Формат:` пропускаются), место = номер
строки (с 1, до 65 535; файл делится по последнему « — »: тире бывает в названии). Название и
автор приводятся к одному виду с обеих сторон:

- название — ключ `normalize_key` (как `title_key`); если точного нет — варианты строки: части
  «А, или Б», без скобок, том после двоеточия / точки («Хроники Нарнии: Принц Каспиан» →
  «принц каспиан»), затем короткая форма названия в каталоге (до `:`, `. `, `(`, «, или»:
  «Мастер и Маргарита: роман»). Сначала точное, затем варианты;
- автор — фамилия (последнее слово каждого автора строки) против любого слова имени автора книги
  (порядок «Шолохов Михаил» и инициалы не мешают); латиница → кириллица по звучанию («Umberto
  Eco»), `ё`/`э` → `е`, `й` → `и`; совпадение — общее начало ≥ min(5, длина) («Стругацкие» ~
  «Стругацкий», «Дойль» ~ «Дойл») или одна правка у слов от 4 букв («Остин» ~ «Остен»).

Название есть, автор другой — места нет (лучше пропуск, чем чужая книга на первом месте).
Первый прогон по `knigi_10_000_progress.txt` (2026-11-17, 418 155 книг): 5445 строк → 3744 с
местом, 1258 нет в каталоге, 432 с другим автором (в каталоге только однофамильцы / одноимённые
книги), 11 повторов. Из нескольких изданий — с обложкой. Список целиком заменяет
`catalog_manual_ranks` одной транзакцией и применяется к слою Б процесса; сервер подхватит опросом.
`--unmatched OUT` — все строки без места в файл по разделам (нет в каталоге, другой автор, повтор). Отчёт: строк, получили место, нет в каталоге, другой автор, повтор, дальше 65 535 (+ по 20
примеров).

Тесты: модульные `books::index` (И между словами, стеммер, точное название, автодополнение, `ё`,
опечатки, автор и серия, фильтры, сортировки, страницы, обновление, перестройка, подсказки, ручные

`books::ranks` (разбор списка и тире в названии, фамилии в любом порядке, латиница, вариант транскрипции, короткие и альтернативные названия, место = строка, чужой автор), `books::search` (параметры →

## Кураторские теги (2026-11-15)

Миграция `20261207100000_catalog_curated_tags.sql` заводит 70 тегов `kind = tag` (арт-направления,
«вайб», сюжетные приёмы, форма повествования: «Артхаус», «Слоубёрнер», «Временная петля» …;
slug — транслит, `avtorskoe-kino`, `festivalnyy-khit`). «Сюрреализм» уже был (`syurrealizm`) —
не дублируется; `ON CONFLICT (slug) DO NOTHING`. Схема не менялась. Привязки к фильмам — не
миграция, а `scripts/catalog-import/tags_llm.py`. Порядок обхода — по убыванию
`entity_stats.tmdb_votes` (есть и у фильмов, и у сериалов; `metadata.popularity` и `rank_score`
у сериалов пусты, по ним сериалы не попадают в выборку). Шаги: `export --dir cache/tags_llm
--offset N --limit M --chunk 100` (пачки `in_NNNN.json`, готовые `out_*.jsonl` пропускаются,
номера продолжают занятые — завтрашний `--offset 10000` не затирает сделанное) → разметка
(`classify` через Claude API либо агенты на Haiku: каждый пишет `out_NNNN.jsonl`) → `apply`
(сухой прогон; запись `--apply`; `--replace` сначала снимает кураторские теги у обработанных
тайтлов, жанры и прочие теги не трогает). `apply` не доверяет ответу модели: теги вне списка
отбрасываются, максимум 3 на тайтл. Теги строгие и редкие: 0–3 на тайтл, пустой список —
обычный ответ; «Авторское кино» / «Артхаус» — только личное высказывание автора, не работа по
найму и не франшиза; теги повода просмотра — не больше одного и 3–5% тайтлов на тег.
Кураторские теги ищутся по имени без учёта регистра и вида: «сюрреализм» (tag) и «магический
реализм» (genre) заведены раньше строчными. Запуск 2026-11-15: топ-10 000 по `tmdb_votes`
(8699 фильмов, 1301 сериал), Haiku; 66% без тегов, 30% с одним; записано 4760 связей.
`cleaned_title`, `is_anime`, `is_valid_title`, `restore_from_archive` остаются в отчёте
(`cache/tags_llm/`, в `.gitignore`) и в БД не пишутся. После записи — `scripts/reindex-search.sh`
(нужен `DEV_LOGIN=true`, иначе 404 на `dev/login`) или кнопка в админке. Список разрешённых
тегов — `TAGS` в скрипте; новый тег = строка в миграции + строка в `TAGS`.

**`related`** в карточке — одна лента для карусели: `[{...EntitySummary, "relation": "prequel"|"sequel"|"remake"}, ...]`, хронологически по `release_date` (без даты — в конце, затем `position`, затем заголовок), пусто — `[]`. Сиквелы, ремейки и приквелы идут **в одной полосе**, тип связи — у каждой карточки. Связи — в самой карточке, а не отдельным запросом: карточка — статика фронтенда, они попадают в HTML.

**Пагинация** списков и поиска: `?limit=20&offset=0` (`limit` 1–100, по умолчанию 20; значения вне
диапазона приводятся к границам). Ответ:

```json
{ "items": [ ... ], "total": 137, "limit": 20, "offset": 0 }
```

В поиске `total` — точное число совпадений Meilisearch (`totalHits`, см. «Точный `total`»).

### Похожие ✅

`GET /entities/{slug}/similar` — через Meilisearch (решение пользователя 2026-10-15: «хотя бы один
общий тег», без подсчёта совпадений). `entities::similar` читает из БД только саму сущность (видима
ли, `kind`), slug'и её тегов и slug'и связанных; список — `search::similar`:

- фильтр `kind = <kind> AND tags IN [<теги сущности>] AND slug NOT IN [<сама и связанные>]` —
  тот же `kind`, хотя бы один общий тег, без самой сущности и её связанных (`related` и так на
  карточке); число общих тегов и жанры на порядок не влияют;
- сортировка `rank_score:desc, release_ts:desc` — балл «Рекомендуемые», затем новее; без значения —
  в конце;
- `limit` 1–24 (12), `offset` нет; `total` — точное число подходящих (`search_exact`);
- нет тегов — пустая страница (`total: 0`), не 404; скрытая сущность — 404; Meilisearch недоступен
  — 503; индекса нет — пустая страница.

До 2026-10-15 был SQL-запрос с весами общих тегов (жанр — 2, тег — 1) по `entity_tags`.

**Валидация баннеров** (`banners::Draft::validate`, 400 `{error, code:"validation", field}`; `field` — путь поля: `title`, `content_html`, `slides[1].image_url`, `buttons[0].label`, `targets[2].pattern`, `exclude_paths[0]`, `ends_at`, …): `title` 1..300; `subtitle`/`slides[].title`/`slides[].subtitle` ≤ 300; `image_url` и `slides[].image_url` — `http(s)://`, `image_url` обязателен при `kind=image`; `link_url`, `slides[].link_url`, `buttons[].url` — `http(s)://` или путь `/…` (не `//`, без пробелов); `content_html` непуст после санитизации при `kind=html`, ≤ 20 000 символов после санитизации; `custom_html` непуст после санитизации при `kind=custom`, ≤ 100 000 символов (до и после санитизации; `field: "custom_html"`); `slides` ≤ 10 и ≥ 1 при `kind=slides`; `buttons` ≤ 3, `label` 1..60, `style` `primary|secondary|ghost`; `theme` из `banners::THEMES`; `targets` 1..20, `page` из `PAGES`, `pattern` — с `/`, ≤ 200, без пробелов, `?`, `#`; `exclude_paths` ≤ 20, те же правила; `ends_at > starts_at`. **Санитизация `content_html`** (`banners::sanitize_html`, `ammonia`; и у `slides[].content_html`): теги `p, br, h2, h3, h4, strong, em, b, i, u, s, span, ul, ol, li, a, img, small, mark` (прочие снимаются, текст остаётся; `script`/`style` — с содержимым); атрибуты `a[href]` (`http(s)://` или `/…`, не `//`; `rel`/`target` не ставятся — их выставляет фронт), `img[src]` (только `https://`), `img[alt, width, height]` (размеры — до 5 цифр), `class` — только классы `text-*`/`font-*` (в т.ч. `text-center|left|right`), остальные вырезаются; `style`, `on*`, `iframe`, `form` — вырезаются. Пусто после очистки — `NULL`.

**Санитизация `custom_html`** (`banners::sanitize_custom_html`, отдельный мягкий builder `ammonia`; поле `custom_html`): теги вёрстки `div, section, article, header, footer, nav, aside, main, p, span, br, hr, h1-h6, strong, em, b, i, u, s, small, mark, sub, sup, del, ins, abbr, time, blockquote, q, cite, code, pre, ul, ol, li, dl, dt, dd, a, img, picture, source, figure, figcaption, table, thead, tbody, tfoot, tr, th, td, caption, colgroup, col, wbr`, `<style>` и svg (`svg, g, path, circle, ellipse, line, polyline, polygon, rect, text, tspan, defs, linearGradient, radialGradient, stop, clipPath, mask, pattern, symbol, use, title, desc`); атрибуты на любом теге `class, style, id, href, src, srcset, alt, width, height, target` (`_blank|_self|_top|_parent`), `rel`, `aria-*`, `data-*` (+ `title, role, lang, dir, sizes, media, type, loading, decoding, colspan, rowspan` и атрибуты рисования svg: `viewBox, xmlns, fill*, stroke*, d, cx, cy, r, rx, ry, x, y, x1..y2, points, transform, opacity, offset, stop-*, gradient*, preserveAspectRatio, clip-path, mask, font-size, font-weight, text-anchor, dominant-baseline`). С содержимым вырезаются `script, iframe, object, embed, form, input, base, meta, link, noscript, template, textarea, select, button, frame, frameset, applet`; все `on*` и HTML-комментарии — всегда. URL (`href`, `src`, `xlink:href`, каждый кандидат `srcset`) — только `http(s)://` или путь `/…` (не `//`); `data:image/*` — только `img[src]`, `#id` — только svg `use`; иначе атрибут снимается. CSS (`style="…"` и содержимое `<style>`, `banners::sanitize_css`): убираются комментарии `/*…*/`, `\`-экраны и `NUL`; вырезаются `expression(`, `javascript:`, `vbscript:`, `behavior:`, `-moz-binding`, `@import …;` целиком; аргумент `url(…)` не `http(s)://`/`/…` → `url()`; до неподвижной точки. | PUT | `/admin/ranking/kinds/{kind}/stream` | Сохранить и применить потоком: `rank` (балл вида в БД), `search` (`index::sync::apply_scores` — пары номер/балл в слой Б, `EntitySidecar::with_scores`: популярность и «Рекомендуемые» без Tantivy; веса поиска). ISR не трогается. 400 / 404 |

**Проверки:** `slug` — `a-z`, `0-9`, одиночные дефисы, до 100 символов; занятый slug — 409.
Названия и имена обязательны, до 300 символов, пробелы по краям обрезаются. `cover_url` и
`photo_url` — только `http(s)://`. `role` — `a-z` и `_` (`actor`, `voice_actor`, `director`,
`writer`, `author`, `composer`, `creator`, ...). Дубль участия — 409, неизвестный `person_id` — 400,
неизвестный тег — 400 со списком таких тегов.

## Постеры и трейлеры: `nexus media`

Медиа — ссылки: `cover_url` и `metadata.trailers` (см. таблицу выше). Ищет и проверяет их
команда приложения (код — `modules/catalog/src/media/`):

```bash
make media                                   # fill: заполнить пустое у всех сущностей
make media MODE=check                        # проверить ссылки, мёртвые заменить
make media ARGS="--dry-run --slug it-2017"   # только показать, что изменилось бы
```

В проде — `nexus media check` по cron раз в сутки ([deploy.md](../deploy.md#постеры-и-трейлеры-по-расписанию)).

| Тип | Постер | Трейлер YouTube | Запасной трейлер |
|---|---|---|---|
| `movie`, `series` | TMDB: русский постер, затем английский, затем без текста; внутри — по голосам | TMDB: только `official`, тип `Trailer`, самый ранний | Rutube |
| `game` | IGDB (`t_cover_big_2x`) | IGDB: релизный / кинематографический трейлер | Rutube |
| `book` | Open Library: по ISBN, иначе по названию и автору | — | — |

Ключи (`infra/.env`, в `.gitignore`): `TMDB_API_KEY` — API key или Read Access Token
(themoviedb.org → Settings → API); `TWITCH_CLIENT_ID`, `TWITCH_CLIENT_SECRET` — приложение на
dev.twitch.tv/console (IGDB принадлежит Twitch). Без ключа источник пропускается, отчёт об этом
предупреждает. Книги и Rutube ключей не требуют.

**Правила:**
- **fill** заполняет только пустое: постер, если нет `cover_url`; YouTube и Rutube, если такого
  источника нет. Подобранное вручную не перезаписывается.
- **check** сначала проверяет текущие ссылки: картинка — `GET` (200 и `image/*`), YouTube —
  oEmbed (отвечает только для существующих видео, которые разрешено встраивать), Rutube —
  `api/video/{id}`. Удаляется только **точно мёртвое** (404, 410, видео скрыто или удалено);
  сеть, 5xx и 403 — «неизвестно», ссылка остаётся: иначе один сбой связи стёр бы все постеры.
  Потом — как fill. Мёртвое без замены просто удаляется: лучше заглушка, чем битая картинка.
- Всё найденное проверяется перед записью. Запись — через ту же проверку `metadata`, что у
  админки, затем `publish::run` (постер есть в поисковом индексе и на странице фронтенда).
- **Rutube** — официальных каналов там нет, поэтому фильтр строгий (`media/pick.rs`): 30 с –
  6 мин; в названии «трейлер»/«тизер», название произведения и только «служебные» слова (год,
  «русский», «дубляж», «4K», слова своего типа — «фильм», «сериал», «игра» и платформы); не
  сиквел («Оно 2»); год, если указан, совпадает. Если в каталоге есть одноимённое произведение
  того же типа (две «Дюны»), год в названии ролика обязателен. Найденное попадает в раздел
  отчёта «Проверить глазами». Тесты фильтра — на настоящих выдачах Rutube, включая его прошлые
  ошибки (трейлер игры вместо фильма, мод, ремастер, фильм целиком).

## Каталог фильмов из TMDB + Wikidata (основной путь)

Три шага, всё в `scripts/catalog-import/`, кэш — `~/.cache/nexus-catalog-import/` (вне репозитория:
`cargo-watch` перезапускал бы приложение на каждую запись):

1. `fetch_tmdb.py` — только скачивание TMDB: все фильмы ежедневного дампа, кроме `video`
   (~1,19 млн, по убыванию popularity), и TMDB id из кэша Wikidata.
   `GET /3/movie/{id}?append_to_response=credits&language=ru-RU`, 40 запросов/с, ответ ужат до
   нужных полей (до 30 актёров, режиссёры) → `tmdb/movies.jsonl`, 404 → `tmdb/missing.txt`. ~8 ч,
   перезапуск продолжает. Ключ — `TMDB_API_KEY` из окружения, корневого `.env` или `infra/.env`
   (v3-ключ или v4-токен).
2. `import_wikidata.py --stage download` и `--stage wiki` — кэш Wikidata (QLever) и Википедии, см.
   ниже; люди — вместе с TMDB id человека (P4985). Этап `load` после появления `catalog_import`
   не запускается: в БД пишет только `merge.py`.
3. `merge.py` — слияние в БД: `DATABASE_URL=… python3 scripts/catalog-import/merge.py` (id архива —
   `--archive-ids FILE` или `--archive-cmd`, по умолчанию
   `docker exec nexus-app target/debug/nexus archive ids`; связь TMDB — в `entities.external_ids`), затем
   `scripts/reindex-search.sh`.

**Один фильм — одна строка.** Схема `catalog_import` (создаёт скрипт, приложение не читает):
`movies` (`entity_id` PK ↔ `tmdb_id` UNIQUE ↔ `qid` UNIQUE, `created`, `written`), `people`
(`person_id` ↔ `tmdb_id` ↔ `qid`, `created`, `written`). Источники связывает сама Wikidata: P4947 —
TMDB id фильма, P4985 — TMDB id человека (у 77% людей фильмов). Фильм ищется по связке, затем среди
готовых непривязанных (сиды) по slug (с годом или без) или «название + год» (они читаются один раз
при старте), и только потом создаётся; slug занят — суффикс `-t<tmdb_id>` / `-q<qid>`. Связки
первого импорта (`wikidata_import`) переносятся при первом запуске; после этого
`DROP SCHEMA wikidata_import CASCADE` безопасен. Если у двух записей Wikidata один TMDB id
(фильм и режиссёрская версия: Apocalypse Now и Redux), id достаётся самой известной; строка,
уже слитая в этом прогоне, второй раз не обновляется (в логе — `conflicts`).

**Поля — первый непустой источник:**

| Поле | Порядок |
|---|---|
| `title` | русское из TMDB → русское из Wikidata → любое (TMDB, затем en Wikidata) |
| `original_title` | TMDB → Wikidata P1476 / en |
| `description` | TMDB (ru) → вступление ru.wikipedia |
| `cover_url` | TMDB `w780` → Commons; несвободные постеры en/ru.wikipedia не используются и удаляются |
| `release_date`, `runtime_min` | TMDB → Wikidata |
| `countries`, `studios`, жанры, режиссёры | объединение обоих (студии — без учёта регистра, до 20) |
| актёры | порядок TMDB (как в титрах), до 15, добор из Wikidata; персонаж — русский из Wikidata, если в TMDB не по-русски |
| люди: `full_name` | русское (Wikidata → TMDB), иначе TMDB / en |
| люди: `photo_url` | TMDB `h632` → Commons |
| люди: `birth_date`, `bio` | Wikidata |

Жанры TMDB → теги по `GENRE_SLUGS` (`import_tmdb.py`, + `music` «Музыка», `tv-movie`
«Телефильм»), Wikidata — по `GENRES`; один набор slug, новые — `kind = genre`.

**Ручные правки не теряются.** В `written` — то, что скрипт записал в каждое поле, и хэши титров и
жанров. Поле обновляется, только если оно пустое или в нём всё ещё записанное скриптом; пустым
значение не затирается (кроме несвободного постера). Титры и жанры заменяются целиком, только
если их не меняли после импорта. У готовых строк (сиды, админка: `created = false`) — только
заполнение пустых полей, титры и жанры не трогаются. Проверено: правка названия, bio и удалённый
актёр пережили повторное слияние; повторный прогон без изменений источников ничего не меняет
(`updated 0`, `people ~0`).

**Скорость** (тест на копии dev: 19 тыс. TMDB + 100 тыс. Wikidata): первый прогон ~180 фильмов/с,
повторный ~480/с (Python ~30%, БД ~70%). Оценка объёма после полного слияния (~1,2 млн фильмов):
PostgreSQL ~5–7 ГБ (`entity_credits` ~8–12 млн строк, люди ~1,5–2 млн), индекс Meilisearch
~5–8 ГБ на версию; кэш TMDB ~4–6 ГБ. Картинки не храним — только ссылки на CDN.

**Лицензии.** TMDB: некоммерческий сайт — бесплатно с атрибуцией (логотип и «This product uses
the TMDB API but is not endorsed or certified by TMDB» — задача фронтенда), коммерческий —
отдельная лицензия TMDB; права на постеры у правообладателей. Wikidata — CC0, тексты Википедии —
CC BY-SA, Commons — по лицензии файла с атрибуцией.

**Активные.** `merge.py` вставляет новые фильмы скрытыми, пишет связь TMDB в `entities.external_ids` и
`entity_stats` (`imdb_id`, `tmdb_votes`, `tmdb_popularity`, если её нет); включает кнопка админки
«Пересобрать активные» ([«Сортировка и активные»](#сортировка-и-активные-)). Привязанные готовые
строки (сиды) получают `active_manual = true`. Первая раскладка на dev (2026-10-12) — ещё
скриптом (40 000 по `vote_count` + 40 000 по `popularity`); её место занимает пересборка по баллу.

**Статистика — `entity_stats`, не `metadata`** (миграция `20261018100000_entity_stats.sql`):
`metadata.popularity`/`vote_count` устарели — `MovieMetadata` их принимает и отбрасывает (старые
формы админки не получают 400), `merge.py` убирает их при записи, разом —
`merge.py --cleanup-metadata` (~25 мин: GIN-индексы). `merge.py --numbers-only` — `entity_stats` из
кэша TMDB пачками (2 мин на 1,2 млн).

## Сортировка и активные ✅

**Статус выхода** — по сегодняшней дате, без заданий: `released` (`release_date ≤ сегодня`), `soon`
(выход в ближайшие `catalog_ranking.soon_days`, 30 дней — «Скоро премьера»), `announced` (позже или
без даты); поле `release_status` в `EntitySummary`, карточке и выдаче поиска. **Видимость**
(`VISIBLE` в `models.rs`, поле `visible` карточки и админского списка): `active` и — для фильмов из
TMDB (`external_ids.tmdb`) — `released` или `soon`, либо `active_manual`. Невышедшие и без даты из TMDB
скрываются сами и сами появляются за `soon_days` дней до выхода (поиск — при ежедневной перестройке
или кнопке); не из TMDB (сиды, админка) и включённые вручную — видны с любой датой. `VISIBLE`
используют списки, карточка (404), похожие, связанные, фильмографии, справочник для `social`,
индексация. Счётчики людей и тегов считают `active` (без окна дат).

**Балл «Рекомендуемые»** (`catalog::ranking`, `modules/catalog/src/ranking.rs`) — сортировка по
умолчанию, у вышедших фильмов с `imdb_votes ≥ min_votes`:
`score = weight_quality·q + weight_popularity·p + weight_recency·r`, где `q` — байесовский рейтинг
IMDb `(v·r + m·C)/(v + m)` (`m` = `trust_votes`, `C` — средний), шкала 5 → 0 … 9 → 1; `p` —
`ln(1+popularity)/ln(1+p99)` (99-й перцентиль TMDB popularity); `r` — `0.5^(возраст/half_life_years)`.
Настройки — `catalog_ranking` (одна строка): по умолчанию 0.5 / 0.3 / 0.2, `trust_votes` 5000,
`half_life_years` 4, `min_votes` 1000, `soon_days` 30. Хранится в `entity_stats.rank_score` и
`quality`; пересчёт — после «Обновить рейтинги» и сохранения настроек (один `UPDATE` узкой таблицы).

**Сортировки** `/entities` (`sort`): `recommended` (по умолчанию, балл; без балла — в конце, по
`tmdb_votes`, затем `tmdb_popularity`), `trending` (TMDB popularity, вышедшие с баллом), `top_rated` (байесовский рейтинг), `new`
(только вышедшие), `soon` (будущие в окне, ближайшие сверху), `popular`/`rating` (наши оценки),
`title`. Фильмы с датой в будущем в публичных списках — только в `soon` («Скоро премьера»), в
остальных сортировках их нет. Поиск: `sort=recommended|trending|top_rated|new|soon|title`
(`rank_score`, `popularity`, `quality`, `release_ts`, `title` — `sortableAttributes`); в поиске
будущие фильмы не скрываются вне `soon`.

**Админка** (запуск вручную, расписания нет; ход — потоком `JobEvent`; одна долгая операция за раз
— общая блокировка с перестройкой поиска, занято — `409` до потока; без Meilisearch — только БД):
- **Обновить рейтинги** — `POST /admin/tmdb/stats/stream`: дамп TMDB `movie_ids_*.json.gz`
  (`TMDB_EXPORTS_URL`, без ключа, ~28 МБ; кроме `video`) → `tmdb_popularity`; IMDb
  `title.ratings.tsv.gz` (`IMDB_DATASETS_URL`, без ключа, ~9 МБ) → `imdb_rating`, `imdb_votes` по
  `imdb_id`; шаги `tmdb_export`, `imdb_ratings`, `stats` (с `progress`), `rank`, затем перестройка
  поиска; `done.stats` — `{tmdb_export, tmdb_updated, imdb_updated, ranked}`. Ошибка скачивания —
  с причиной (`… Connection refused`). Некоторые DNS (Яндекс `77.88.8.8`, часть провайдеров)
  отвечают на `files.tmdb.org` заглушкой `127.0.0.1`: в dev у `app` — `dns: [1.1.1.1, 8.8.8.8]`
  (`infra/docker-compose.yml`), на проде нужен такой же резолвер или зеркало (`TMDB_EXPORTS_URL`).
- **Пересобрать активные** — `POST /admin/tmdb/active/stream?count=80000` (0–1000000; 250 000 —
  `?count=250000`): из связанных с TMDB без `active_manual` активны топ `count` вышедших по баллу
  (без балла — по `tmdb_votes`, `tmdb_popularity`) и все `soon`; остальные (в том числе анонсы и без
  даты) скрыты. Один `UPDATE` разницы (операторный триггер сдвигает счётчики), затем перестройка
  поиска с `force` и ISR `{"all": true}`; `done.active` — `{activated, deactivated, soon, active}`.
  Сначала — «Обновить рейтинги»: топ по текущему баллу.
- **Настройка сортировки** — `GET /admin/ranking`; `POST /admin/ranking/preview?limit=50` (тело —
  настройки, топ вышедших по формуле с составляющими `q_part`, `p_part`, `r_part` и `active`, ничего
  не пишет — подбирать веса на глаз); `PUT /admin/ranking/stream` (сохранить, `rank`, перестройка
  поиска с `force`). Проверка: веса 0–10, `half_life_years` 0.1–100, голоса 0–10 000 000,
  `soon_days` 0–365, иначе 400.
- Редакционные подборки («Выбор редакции») — позже.

Лицензии: IMDb datasets — только личное и некоммерческое использование (как бесплатный TMDB);
коммерческий запуск — лицензия IMDb.

Тесты: `unreleased_tmdb_films_are_hidden_until_soon`, `ranking_preview_and_save`,
`search_skips_hidden_and_sorts_by_stats`, `legacy_metadata_tmdb_keys_are_dropped`,
`stats_refresh_from_tmdb_and_imdb` (фейковые дампы TMDB и IMDb, повтор — 0 изменений),
`active_rebuild_by_count_keeps_soon_and_manual`; разбор дампов — модульные тесты.

## Импорт фильмов из TMDB

`scripts/catalog-import/import_tmdb.py` (Python: `aiohttp`, `asyncpg`, `requirements.txt` рядом) —
массовая загрузка фильмов прямо в PostgreSQL, в обход API. Запуск:
`TMDB_API_KEY=… DATABASE_URL=postgres://… python3 scripts/catalog-import/import_tmdb.py`, затем
`scripts/reindex-search.sh` (Meilisearch о новых строках не знает).

- **Extract:** ежедневный дамп `movie_ids_MM_DD_YYYY.json.gz` с `files.tmdb.org/p/exports` (нет
  сегодняшнего — до 3 дней назад, кэш `~/.cache/nexus-catalog-import/tmdb`), без `adult`/`video`, `popularity > 15`
  (`--min-popularity`), не больше 50 000 самых популярных (`--limit`). `--ids` — свой список.
- **Transform:** `GET /3/movie/{id}?append_to_response=credits&language=ru-RU`, 32 воркера
  (`--workers`), общий лимит 40 запросов/с (`--rate`; TMDB пускает ~50 с IP), повторы на 429
  (`Retry-After`), 5xx и сетевые ошибки. Ключ v3 — параметром `api_key`, токен v4 (`eyJ…`) — `Bearer`.
  `entities`: `kind = movie`, `title` (русское), `original_title`, `description` (overview),
  `release_date`, `cover_url` (`image.tmdb.org/t/p/w780…`); `metadata` — только `runtime_min`
  (1–10000), `countries` (alpha-2, верхний регистр), `studios` (до 20 по ≤120 символов), без
  дублей — как нормализует `metadata.rs`. Титры: режиссёры (`director`, позиции с 0), затем первые
  15 актёров по порядку TMDB (`actor`, `character_name`); `people.photo_url` — `…/h632…`. Жанры —
  теги `kind = genre`; id жанра TMDB сопоставлен slug сидовых тегов (`878 → sci-fi`,
  `9648 → detective`, …), существующие теги не меняются.
- **Slug:** латинский `original_title` (как в сидах: `dune-2021`), иначе транслит русского названия
  (`brat-1997`), плюс год. Людей — по имени (`timothee-chalamet`); имя без латиницы и кириллицы —
  `person-<tmdb_id>`.
- **Load:** один писатель, пачка 500 фильмов (`--batch-size`) — одна транзакция, вставка через
  `unnest(массивы)` (нет лимита в 65 535 параметров) с `ON CONFLICT DO NOTHING` во всех таблицах;
  id — `DEFAULT uuidv7()` базы.
- **Перезапуск** безопасен: служебная схема `tmdb_import` (создаёт скрипт, приложение и миграции её
  не используют; удалить — `DROP SCHEMA tmdb_import CASCADE`): `movies` (`tmdb_id` → `entity_id`,
  `created`, `details`), `people` (`tmdb_id` → `person_id`), `skipped` (404 и фильмы без названия). Загруженные
  и пропущенные id не запрашиваются повторно; оборванная пачка не закоммичена и загрузится заново.
  FK с `ON DELETE CASCADE`: удалённая в админке сущность при следующем запуске вернётся.
- **Существующие данные не перезаписываются.** Свободный slug — фильм создаётся. Занятый фильмом,
  ещё не привязанным к TMDB (сиды, админка), — это тот же фильм, он привязывается (`created = false`)
  без изменений, его титры и жанры не трогаются. Занятый другим фильмом TMDB или сущностью другого
  типа — slug `<slug>-<tmdb_id>` (`dune-2021-1001`). Люди — так же: тёзка получает `john-smith-502`.
- **Без ключа API** (`--export-only`, нужен только `DATABASE_URL`): все фильмы дампа, кроме
  `adult`, по убыванию popularity — только `title` = `original_title` и `original_title`; ни года,
  ни описания, постера, людей и жанров (их отдаёт лишь API с ключом). Slug — из оригинального
  названия без года (`hamlet`, следующие — `hamlet-10264`), сиды с этим не совпадают: в базе будут
  и `dune-2021`, и `dune`. Строки помечены `tmdb_import.movies.details = false`; убрать —
  `DELETE FROM entities WHERE id IN (SELECT entity_id FROM tmdb_import.movies WHERE created AND
  NOT details)`. Обычный запуск с ключом такие фильмы считает загруженными и не дополняет.
- Не загружаются: `birth_date`/`bio` людей (нужен отдельный запрос на человека), трейлеры,
  возрастной рейтинг. В проде TMDB требует атрибуцию на сайте.

## Импорт фильмов из Wikidata (без ключей)

`scripts/catalog-import/import_wikidata.py` (те же `aiohttp`, `asyncpg`; общие функции slug — из
`import_tmdb.py`) — 100 000 фильмов с людьми, жанрами и студиями. Запуск:
`DATABASE_URL=postgres://… python3 scripts/catalog-import/import_wikidata.py`, затем
`scripts/reindex-search.sh`. Этапы (`--stage download|wiki|load`, по умолчанию все), кэш
`~/.cache/nexus-catalog-import/wikidata` (~230 МБ; не в репозитории — `cargo-watch` перезапускал бы
приложение на каждую запись, обрывая перестройку поиска):

- **download** — 6 SPARQL-запросов к QLever (`qlever.cs.uni-freiburg.de/api/wikidata`, полная
  Wikidata, сотни тысяч строк за секунды; официальный `query.wikidata.org` режет запросы на 60 с и
  на 100 фильмов с актёрами не укладывается). Фильмы — `P31` ∈ {Q11424 фильм, Q24869
  полнометражный, Q202866 анимационный, Q29168811 полнометражный мультфильм}, топ `--limit`
  (100 000) по числу статей в Википедиях (sitelinks; при 100 000 — от 3 статей). Ответы — CSV:
  `films`, `basics`, `credits`, `people`, `characters`, `facets`; всё — около 35 с.
  У QLever sitelinks — `xsd:int`, сравнивается только через `xsd:integer(STR(?l))`.
- **wiki** — MediaWiki API: ru.wikipedia — вступление статьи (`description`) и картинка статьи
  (постер, `pilicense=any`), без постера — из en.wikipedia. 20/50 заголовков на запрос. Нужен контакт
  в User-Agent: `WIKIMEDIA_CONTACT=<почта или URL>` — без него Википедия после пары запросов отвечает
  429 с `Retry-After: 100`. С контактом — `--wiki-concurrency 4 --wiki-rate 4` (по умолчанию 1 и
  1/с; ответ на 20 статей идёт ~6 с, так что последовательно — ~2 ч). Около 3 300 запросов, кэш
  `wiki.jsonl` докачивается после остановки.
- **load** — пачка 500 фильмов = одна транзакция, `unnest` + `ON CONFLICT DO NOTHING`, id —
  `uuidv7()`. Описания и постеры, докачанные позже, вписываются в пустые поля уже созданных
  импортом фильмов при следующем `--stage load`.

Поля: `title` — подпись ru (иначе en / P1476), `original_title` — P1476 (иначе en),
`release_date` — самая ранняя P577 с точностью до дня (год для slug — с любой точностью),
`metadata.runtime_min` — P2047 в минутах (часы и секунды пересчитываются), `countries` — P495 →
P297, `studios` — P272 (до 20 по ≤120 символов). Жанры — P136 и P31 по таблице `GENRES`
(`Q130232 драматический фильм → drama`, `Q1200678 фильм-тайна → detective`, `Q202866 → animation`, …,
26 тегов `kind = genre`, новые: comedy, action, crime, romance, documentary, musical, biography,
war, western, history, family, sport). Титры: режиссёры P57, затем 15 актёров P161 и актёров
озвучивания P725 — по порядку P1545, без него самые известные первыми (sitelinks); персонаж —
подпись P453 (ru, иначе en) или P4633. Люди: `full_name` — ru, иначе en/`mul` (с 2024 имена
людей в Wikidata часто только в `mul`), `birth_date` — P569 с точностью до дня, `photo_url` —
P18 через `commons.wikimedia.org/wiki/Special:FilePath/…?width=400`, `bio` — краткое описание ru
(«Американский режиссёр.»).

Slug: латинский оригинал, иначе английское название (как в сидах: `stalker-1979`), иначе транслит
русского, плюс год (`inception-2010`); занят — `<slug>-q<qid>`. Люди — по имени
(`christopher-nolan`), известные первыми. **Существующие данные не перезаписываются:** готовый
непривязанный фильм с тем же slug (с годом или без — `interstellar`) или с тем же названием и годом
(`lotr-fellowship-2001`) привязывается без изменений, его титры и жанры не трогаются; люди — по
slug. Служебная схема `wikidata_import` (скрипт создаёт сам, приложение не читает): `movies`
(`qid` → `entity_id`, `created`, `tmdb_id` — P4947, для будущего обогащения из TMDB), `people`
(`qid` → `person_id`). Убрать загруженное — `DELETE FROM entities WHERE id IN (SELECT entity_id
FROM wikidata_import.movies WHERE created)`, затем `DELETE FROM people WHERE id IN (SELECT
person_id FROM wikidata_import.people) AND NOT EXISTS (SELECT 1 FROM entity_credits c WHERE
c.person_id = people.id)` и `DROP SCHEMA wikidata_import CASCADE`.

**Покрытие (почему не все фильмы).** Каталог берёт 100 000 самых известных фильмов Wikidata — это
`--limit`, а не предел источника:

| Срез Wikidata (QLever, 2026-10-12) | Фильмов |
|---|---|
| `P31` ∈ наши 4 типа (фильм, полнометражный, анимационный, полнометражный мультфильм) | 354 685 |
| из них со статьёй хотя бы в 2 Википедиях | 204 456 |
| загружено (топ-100 000, от 3 статей) | 99 616 + 14 сидов |
| не берём: короткометражные `Q24862` / анимационные короткометражки `Q17517379` | 49 780 / 5 647 |
| не берём: телефильмы `Q506240` | 22 722 |

- Остальные ~250 тыс. фильмов наших типов — с 0–2 статьями: малоизвестные, часто без постера,
  описания и состава. Взять больше — `--limit 200000` (или `--limit 400000 --min-links 0`), всё
  остальное (кэш, перезапуск, привязка) работает так же; QLever отдаёт такие объёмы за секунды,
  дольше всего — Википедия.
- Сама Wikidata знает не все фильмы: у TMDB ~1,25 млн записей (вместе с любительскими видео),
  в Wikidata — около 355 тыс.; в неё попадают в основном фильмы со статьёй в Википедии.
- Типы: фильм с `P31` = «немое кино», «аниме-фильм» и т. п. без одного из наших 4 типов не
  выбирается (у большинства есть и `Q11424`). Короткометражки и телефильмы — осознанно не берём.
- Русское название (подпись `ru`) — у 36 421 из 99 616 загруженных, у остальных `title` —
  английское; описание (статья ru.wikipedia) — у ~31 тыс., постер — у ~83 тыс.
- Пропущено 370 фильмов без подписи ни `ru`, ни `en`.

Первый прогон (2026-10-11, dev): 99 616 фильмов (+14 сидов привязано, 370 без названия на ru/en
пропущено), 137 538 людей, 765 003 титра, 135 781 связь с жанрами, 0 конфликтов slug; download
35 с, load 2 мин 40 с; wiki (4 параллельных запроса) — ~40 мин, описания/постеры у 83 400 фильмов. Лицензии: данные Wikidata — CC0, тексты Википедии — CC BY-SA (нужна
атрибуция), фото Commons — свободные с атрибуцией, постеры из статей обычно несвободные
(добросовестное использование) — для прода нужно решение по правам.
