# Модуль `auth`

**Отвечает за:** регистрацию, вход, выдачу и обновление токенов, профиль пользователя, роли.
**URL:** `/api/auth` · **Код:** `modules/auth/` (выдача токенов), `libs/shared/src/auth.rs` (проверка
токенов и ролей — ей пользуются все модули).

**Статус:** ✅ регистрация, вход, refresh, выход, профиль, роли, админские эндпоинты.

## Роли

| Роль | Кто это | Что может |
|---|---|---|
| гость | без токена | Читать каталог и форум |
| `user` | любой зарегистрированный | + отзывы и оценки, коллекции, **ответы в темах форума** |
| `author` | назначает админ | + **создавать форумы и темы** |
| `admin` | назначает админ | + админские эндпоинты (`/api/<модуль>/admin/...`) |

Роли упорядочены: `user < author < admin`. Каждая следующая умеет всё, что умеют предыдущие.
Новый пользователь всегда получает `user`. Повысить роль может только админ.

### Как проверять права в коде

Извлечение пользователя и проверка ролей лежат в `shared`, поэтому любой модуль может проверять
права, не завися от `auth`.

```rust
use shared::{AdminUser, AuthUser, Role};

// Нужен любой вошедший пользователь (иначе 401)
async fn create_review(user: AuthUser, ...) -> AppResult<...> { ... }

// Нужна роль не ниже author (иначе 403)
async fn create_thread(user: AuthUser, ...) -> AppResult<...> {
    user.require(Role::Author)?;
    ...
}

// Только админ: 401 без токена, 403 с другой ролью
async fn admin_action(AdminUser(admin): AdminUser, ...) -> AppResult<...> { ... }
```

## Токены (JWT)

| | Access-токен | Refresh-токен |
|---|---|---|
| Что это | JWT (HS256), подписан `JWT_SECRET` | Случайная строка, 64 hex-символа |
| Живёт | 15 минут | 30 дней |
| Где хранится на сервере | нигде, проверяется по подписи | хеш SHA-256 в `refresh_tokens` |
| Как передаётся | `Authorization: Bearer <token>` | в теле `/refresh` и `/logout` |
| Содержимое | `sub` (id пользователя), `role`, `iat`, `exp` | — |

**Как работает:**
1. `login` или `register` → пара токенов.
2. Клиент ходит в API с access-токеном.
3. Access истёк (401) → `refresh` → **новая** пара. Старый refresh-токен отзывается (ротация).
4. `logout` → refresh-токен отозван. Access доживает свои ≤15 минут.

**Защита:**
- **Повторное использование refresh-токена.** Если уже отозванный токен пришёл снова, значит, его
  украли или клиент сломан. Тогда отзываются **все** сессии пользователя.
  Следствие для фронтенда: два параллельных `refresh` с одним токеном разлогинят пользователя,
  поэтому запросы на обновление нужно выстраивать в очередь.
- **Смена роли и блокировка** вступают в силу при следующем `refresh`, то есть не позже чем через 15 минут.
  Заблокированному (`is_active = false`) refresh не выдаётся.
- **Неверный логин, неверный пароль и заблокированный аккаунт** дают одинаковый 401. Пароль
  проверяется даже для несуществующего логина, чтобы по времени ответа нельзя было понять, есть ли он.
- **Пароли** хешируются Argon2id, в отдельном пуле потоков, чтобы не тормозить остальные запросы.

**`JWT_SECRET`:** не короче 32 символов, иначе приложение не стартует. В dev задан в
`docker-compose.yml`. В проде обязательно свой: `openssl rand -base64 48`. Смена секрета
делает недействительными все access-токены, refresh-токены продолжают работать.

## Эндпоинты

| Метод | Путь | Доступ | Что делает |
|---|---|---|---|
| POST | `/api/auth/register` | все | Регистрация → 201 + пара токенов |
| POST | `/api/auth/login` | все | Вход по email или username → пара токенов |
| POST | `/api/auth/refresh` | все | Новая пара токенов по refresh-токену |
| POST | `/api/auth/logout` | все | Отзыв refresh-токена → 204 |
| GET | `/api/auth/me` | вошедший | Свой профиль |
| GET | `/api/auth/admin/users?limit=&offset=` | admin | Список пользователей (до 100 за раз) |
| PATCH | `/api/auth/admin/users/{id}/role` | admin | Сменить роль. Понизить себя нельзя |

Примеры запросов с проверками — `http/auth.http`.

**Регистрация, правила полей:**
- `email` — с `@` и точкой в домене, без пробелов.
- `username` — 3–32 символа: латиница, цифры, `_`, `-`, `.`.
- `password` — 8–128 символов.
- `display_name` — до 64 символов, необязательно.

Email и username уникальны **без учёта регистра**.

**Ответ `login` / `register` / `refresh`:**
```json
{
  "access_token": "eyJ...",
  "token_type": "Bearer",
  "expires_in": 900,
  "refresh_token": "6535d106...",
  "user": { "id": "…", "email": "user@nexus.local", "username": "user", "display_name": "…",
            "avatar_url": null, "role": "user", "is_active": true, "created_at": "…" }
}
```

**Ошибки:** `400` — невалидные поля, `401` — нет токена, токен недействителен или неверный логин,
`403` — роль ниже нужной, `409` — email или username заняты. Тело: `{"error": "..."}`.

## Таблицы

### `users` ✅ — пользователи

Аккаунт пользователя. На `users.id` ссылаются почти все социальные таблицы.

| Колонка | Тип | Ограничения | Описание |
|---|---|---|---|
| `id` | `uuid` | PK | Идентификатор |
| `email` | `citext` | NOT NULL, UNIQUE | Email; уникален без учёта регистра (`Ivan@Mail.ru` = `ivan@mail.ru`) |
| `username` | `citext` | NOT NULL, UNIQUE | Логин, тоже без учёта регистра |
| `password_hash` | `text` | NOT NULL | Хеш Argon2id. Сам пароль не хранится |
| `display_name` | `text` | | Отображаемое имя |
| `avatar_url` | `text` | | Ссылка на аватар |
| `role` | `user_role` | NOT NULL, default `user` | Роль: `user`, `author`, `admin` |
| `is_active` | `boolean` | NOT NULL, default `true` | `false` — аккаунт заблокирован, вход и refresh запрещены |
| `created_at` | `timestamptz` | NOT NULL | Дата регистрации |
| `updated_at` | `timestamptz` | NOT NULL | Обновляется триггером |

**`user_role`** — enum (`user`, `author`, `admin`). Порядок значений задаёт старшинство, поэтому в
SQL работает `role >= 'author'`.

### `refresh_tokens` ✅ — сессии пользователя

Каждая запись — одна сессия (одно устройство или вход).

| Колонка | Тип | Ограничения | Описание |
|---|---|---|---|
| `id` | `uuid` | PK | Идентификатор сессии |
| `user_id` | `uuid` | NOT NULL, FK → `users`, CASCADE | Чья сессия |
| `token_hash` | `text` | NOT NULL, UNIQUE | **SHA-256** токена. Даже утечка таблицы не даст войти |
| `expires_at` | `timestamptz` | NOT NULL | Когда истекает (выдача + 30 дней) |
| `revoked_at` | `timestamptz` | | Когда отозван (ротация, выход, подозрение на кражу). `NULL` — активен |
| `user_agent` | `text` | | Браузер или устройство, для будущего списка «активные сессии» |
| `ip` | `inet` | | IP при входе (из `X-Real-IP` от nginx) |
| `created_at` | `timestamptz` | NOT NULL | Когда выдан |

**Индексы:** по `user_id` (все сессии пользователя); частичный по `expires_at` для неотозванных
(фоновая чистка просроченных 🕓).

### `user_interests` 🕓 — интересы пользователя

Основа столпа «реалтайм по интересам» (см. [vision](../vision.md)): на какие сущности подписан
пользователь. Набросок: `user_id` → `users`, `entity_id` → `entities`, `created_at`, PK по паре.

> Вопрос на обсуждение: интересы — это данные пользователя (`auth`) или социальная связь с
> контентом (`social`)? Таблица ссылается на `entities`, и ей пользуются лента и `realtime`,
> поэтому логичнее положить её в `social`.
