# Замер: карточки каталога через кэш (2026-10-07)

Задержка карточек `GET /catalog/entities/{slug}` и `GET /catalog/people/{slug}` по уровням кэша
L1 (память) → L2 (Redis) → L3 (Meilisearch) в сравнении с PostgreSQL, в dev-сборке и в продовом
образе. Как устроен кэш — [catalog.md](../modules/catalog.md#кэш-карточек-людей-).

> С 2026-10-08 карточки сущностей через кэш не идут: `GET /entities/{slug}` читает PostgreSQL, страницы
> отдаёт статика фронтенда (ISR). Цифры по сущностям ниже — для прежней схемы.

## Как мерили

- Одна машина, всё в Docker: nginx → приложение → Redis, Meilisearch, Postgres.
  - **Dev:** `make up`, `cargo run`, debug-сборка, порт 80.
  - **Release:** образ `make image` (`cargo build --release`) с `infra/docker-compose.prod.yml`
    рядом с dev, порт 8088 ([deploy.md](../deploy.md#проверка-локально-без-сервера)).
- Данные — `make seed`: 46 сущностей, 38 человек.
- Скрипт — `scripts/bench/cards.sh` (клиент на Python, `http.client`):
  - перезапуск приложения: L1 пуст, а стартовая перестройка индексов очищает Redis;
  - **L3** — первый запрос к каждой карточке;
  - **L2** — первый запрос к каждой карточке через 31 с, когда L1 истёк, а Redis ещё полон;
  - **L1** — 500 повторных запросов одной карточки;
  - для сравнения — `/health` (пустой запрос) и список `/entities?limit=20` из PostgreSQL;
  - пропускная способность — `ab -k -n 20000 -c 50`.

Повторить:

```bash
scripts/bench/cards.sh dev http://localhost docker compose -f infra/docker-compose.yml
scripts/bench/cards.sh release http://localhost:8088 \
  docker compose -f infra/docker-compose.prod.yml --env-file /tmp/nexus-local.env
```

## Задержка одного запроса

Медиана (p50), соединение keep-alive (как у браузера). С новым соединением на каждый запрос (как у
`curl`) — примерно +0.3 мс.

## Выводы

1. **Release быстрее dev в 2–2.7 раза** на всём пути запроса — это цена сборки без оптимизаций.
2. **Карточка из L1 в release на 0.13 мс дольше пустого `/health`.** Остальное время — сеть,
   docker-proxy и nginx, а не кэш.
3. **L2 (Redis) локально почти как L1**: Redis рядом в сети Docker. Польза L2 — общий кэш для всех
   инстансов и для перезапусков, а не скорость.
4. **L3 (Meilisearch) примерно на 0.3 мс дольше кэша.** Платит только первый запрос к карточке.
5. **Под нагрузкой карточка из кэша держит в 2.4 раза больше запросов**, чем список из PostgreSQL.
   На большом каталоге разрыв с БД вырастет, а время кэша — нет.
6. **Потолок стенда — около 3 600 req/s даже для `/health`**: nginx открывает к приложению новое
   TCP-соединение на каждый запрос (`proxy_pass` через переменную, без `upstream keepalive`), а `ab`
   работает на той же машине. 🕓 Включить keep-alive между nginx и приложением.
7. **Время запроса в браузере** (вкладка Network) больше этих цифр: туда входит работа самого
   браузера. На проде к любому запросу прибавится путь по интернету (20–80 мс) и TLS, а docker-proxy
   из пути уйдёт (внешний трафик перенаправляет ядро через iptables).

Оговорки: клиент, nginx, приложение и все сервисы делят один процессор, поэтому важны соотношения,
а не абсолютные числа. Python-клиент добавляет к каждому замеру около 0.1 мс. Сравнение с БД сделано
на списке; старая карточка из PostgreSQL (3 SQL-запроса) стоила бы примерно столько же.
